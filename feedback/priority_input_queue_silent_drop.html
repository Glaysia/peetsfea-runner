[버그] 우선순위 입력큐 제출이 조용히 드롭됨 intake(:7875)는 accepted를 돌려주지만, 제출한 sweep이 실제로는 priority_sweeps에 안 들어가 워커가 영원히 처리하지 않음. 클라이언트는 성공으로 오인.

심각도: 높음 (silent data loss) edt_intake.pysingle_simulation_store.pypostgres_store.py

1증상 (실측)

우선순위 클라이언트(어댑티브 샘플러)가 서브셋 toml 5건을 count=20으로 제출. intake 응답은 전부 정상:

POST :7875/submit ×5
→ {"accepted": 20, "request_id": "sweep-1", "batch": 1}
→ {"accepted": 20, "request_id": "sweep-2", "batch": 2} ... sweep-5

그러나 곧바로 대시보드/큐를 보면 제출분이 어디에도 없음:

확인결과
GET :7875/healthpriority_depth = 0
GET :8080/api/queue{"depth":0,"items":[]}
최근 결과 /api/results전부 base-* (baseline). sweep-* 0건
워커 9개 (SLURM RUNNING)전부 baseline만 처리, 우선순위 sweep 미처리
즉: intake가 accepted로 응답한 100건이 실제 큐(priority_sweeps)에 들어가지 않아 영구 유실. HTTP 200이라 클라이언트는 알 길이 없음.

2근본 원인 (코드 3개 조합)

① request_id가 인메모리 카운터라 재시작마다 sweep-1로 리셋

peetsfea_runner/edt_intake.py

_seq: int = field(default=0, init=False)        # L97 — 프로세스 메모리에만 존재
def _next_seq(self) -> int:                       # L100
    with self._seq_lock:
        self._seq += 1
        return self._seq

batch = self._next_seq()                          # L124
request_id = f"sweep-{batch}"                   # L125 — 영속 X

_seq는 데몬 메모리에만 있어 intake 재시작/재배포 때마다 0으로 리셋 → 발급되는 request_id가 sweep-1, sweep-2, …로 이전 세션과 반복됨. (패치/재시작이 잦은 환경에서 항상 충돌 후보.)

② 같은 request_id는 조용히 무시 (PK 충돌 → DO NOTHING)

priority_sweeps.request_id 는 PRIMARY KEY이고, 두 백엔드 모두 충돌 시 그냥 버림:

# single_simulation_store.py L416~423 (DuckDB)
INSERT OR IGNORE INTO priority_sweeps (...) VALUES (...)

# postgres_store.py L428~436 (Postgres)
INSERT INTO priority_sweeps (...) VALUES (...) ON CONFLICT (request_id) DO NOTHING

주석도 "같은 request_id는 무시". 재시작 후 재사용된 sweep-N이, 아직 lease/삭제되지 않고 남아있는 같은 id 행과 충돌하면 신규 제출이 통째로 드롭. (lease 완료 시 행을 DELETE하지만, 미완료/대기 중이면 잔존.)

③ intake가 삽입 성공 여부와 무관하게 accepted 반환 (거짓 성공)

# edt_intake.py L126~129
self.queue.enqueue_sweep(request_id=request_id, ...)   # 반환값 없음(None) — 삽입 여부 모름
return {"accepted": raw_count, "request_id": request_id, "batch": batch}

enqueue_sweep/priority_enqueue_sweep는 -> None이라 실제 INSERT가 무시됐는지 알 수 없고, submit()은 무조건 accepted를 돌려줌 → 유실을 성공으로 보고.

연쇄: ①재사용 id + ②충돌 시 silent drop + ③무조건 accepted = 재시작 후 우선순위 제출이 조용히 사라지는데 클라이언트는 성공으로 오인. 어댑티브 샘플링이 통째로 무효가 됨.

3권장 수정

핵심: request_id를 전역 유일·영속으로 만들고, 삽입 결과를 호출자에게 정직하게 돌려줄 것.

A. request_id를 유일하게 (인메모리 시퀀스 폐기)

  • 옵션 1 — store가 발급: DB 시퀀스/SERIAL, 또는 max(seq)+1을 트랜잭션 내에서.
  • 옵션 2 — 충돌 불가능한 토큰: f"sweep-{uuid4().hex}" 또는 f"sweep-{epoch_ns}-{rand}". (가장 간단, 권장)
# 예: edt_intake.py
import uuid
request_id = f"sweep-{uuid.uuid4().hex[:16]}"     # 재시작 무관 유일

B. 삽입 실패를 표면화 (silent drop 금지)

  • priority_enqueue_sweep가 실제 삽입 행수(rowcount)를 반환하도록. DuckDB/Postgres 모두 INSERT … (OR IGNORE / ON CONFLICT DO NOTHING) 후 rowcount 확인 가능.
  • submit()은 삽입 0이면 accepted 대신 명확한 상태(예: 409 conflict 또는 {"accepted":0,"reason":"duplicate_request_id"}) 반환.
inserted = self.queue.enqueue_sweep(...)          # bool/rowcount 반환하도록 변경
if not inserted:
    return {"accepted": 0, "reason": "duplicate_request_id", "request_id": request_id}, 409
return {"accepted": raw_count, "request_id": request_id}

A를 적용하면 충돌 자체가 사라지므로 B는 방어선(회귀 감지)용.

C. (점검) intake와 lease/dashboard가 같은 store를 보는가

최근 Postgres 백엔드 토글(EDT_STORE_BACKEND) 도입 이후라, intake(:7875) / lease(:7878) / dashboard(:8080) 세 서비스가 동일 backend·동일 DB(EDT_STORE_BACKEND, db_path/DSN)를 보는지 확인 필요. 한쪽만 postgres이고 다른 쪽이 duckdb면, 제출은 한 store에 들어가고 lease는 다른 store를 비워 보게 되어 동일 증상(depth 0, 미처리)이 납니다.

4재현 / 검증

# 재현
1) 제출 A: POST /submit {sweep_toml_text, count:20}  → sweep-1 적재
2) intake 데몬 재시작 (또는 _seq 리셋되는 상황)
3) 제출 B: POST /submit {...}  → 다시 sweep-1 발급 → sweep-1 잔존 시 DROP, 그래도 200 accepted

- 워커 결과(request_id)가 sweep-*(우선순위)로 기록됨
