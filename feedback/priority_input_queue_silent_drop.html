1활성 장애 — enqueue 쓰기가 store에 안 남음 지금 이걸 먼저

control_plane 구조상 한 web 프로세스가 store 1개를 공유합니다:

# edt_control_plane.py
store  = make_result_store(config.db_path)                 # L270
intake = IntakeService(queue=DbPriorityQueue(store=store))  # L304
start_priority_lease_server(queue=self.intake.queue, ...)    # L211 (같은 큐)
start_dashboard(store=self.store, ...)                       # L202 (같은 store)
# edt_intake.py — /health 도 submit과 같은 큐를 읽음
/health → {"priority_depth": service.queue.depth()}      # L141 → store.priority_depth()
submit  → service.queue.enqueue_sweep(...)             # L126 → store.priority_enqueue_sweep()
모순: submit과 /health가 같은 store 객체를 쓰고 읽습니다. sweep-7이 INSERT되고 커밋됐다면 priority_depth(= SELECT sum(remaining_count) FROM priority_sweeps)가 반드시 증가해야 하는데 0 그대로 → enqueue의 INSERT가 그 store에 실제로 남지 않았다는 뜻.

유력 원인 (호스트에서 확인 필요)

  1. (최우선) 돌고 있는 :7875 데몬이 이 코드가 아님 — 패치가 실제 배포/재시작 안 됨. 응답이 accepted·batch 증가하는 건 옛 코드여도 동일할 수 있음. 먼저 배포 버전·재시작 여부 확인.
  2. backend 쓰기/가시성 불일치 — EDT_STORE_BACKEND가 의도와 다르거나(duckdb↔postgres), DuckDB의 별도 연결이 미커밋 쓰기를 못 보거나, priority_sweeps가 read와 다른 DB/DSN에 생성됨. (Postgres는 autocommit=True라 정상이어야 함 → 1번이 더 의심.)
  3. initialize()가 priority_sweeps를 엉뚱한 DB에 만들거나, enqueue 경로가 baseline 리필 store와 분리됨.
호스트에서 1초 판별: 제출 1건 직후 활성 DB에 직접 — 
SELECT count(*), COALESCE(sum(remaining_count),0) FROM priority_sweeps;
0이면 enqueue 쓰기가 안 들어가는 것(배포/백엔드 문제) → 여기부터 고쳐야 함. 0이 아니면 lease/분배 쪽 문제.

2설계 버그 — request_id ①을 고쳐도 재발

② request_id가 인메모리 순번 → 재시작 시 sweep-1부터 반복

# edt_intake.py
_seq: int = field(default=0, init=False)    # L97 프로세스 메모리에만 존재 → 재시작 시 0
request_id = f"sweep-{self._next_seq()}"   # L125 sweep-1, sweep-2, … 반복

③ 중복이면 조용히 버림 + 그래도 accepted

# 두 backend 모두 중복 request_id(PK) → silent drop
single_simulation_store.py:423   INSERT OR IGNORE INTO priority_sweeps ...
postgres_store.py:436            INSERT ... ON CONFLICT (request_id) DO NOTHING

# edt_intake.py L126-129 — 삽입 여부 모른 채 무조건 성공 보고
self.queue.enqueue_sweep(...)         # -> None (삽입행수 안 돌려줌)
return {"accepted": raw_count, ...}     # 거짓 성공 가능
→ intake 재시작 후 재사용된 sweep-N이 잔존 행과 충돌하면 제출이 통째로 드롭되는데 HTTP 200 accepted. (①과 별개로 반드시 존재하는 위험.)

3권장 수정

①(활성): 위 1초 판별로 "쓰기가 안 남는" 지점부터 — 배포 버전/재시작, EDT_STORE_BACKEND·DSN·db_path 일관성, priority_sweeps 실제 행 생성 확인.
②③(설계):
  • request_id를 UUID로 — 인메모리 순번 폐기, 재시작·중복과 무관하게 유일: 
    import uuid
request_id = f"sweep-{uuid.uuid4().hex}"
  • enqueue가 삽입행수 반환 → submit()이 0이면 accepted 대신 정확한 상태(409 / {"accepted":0,"reason":"duplicate"}). silent drop이 거짓 성공으로 새지 않게.
