1솔브 = 1컨테이너 아키텍처 제안 · 미구현

잡당 1 서브 오케스트레이터가 단명(短命) enroot 컨테이너를 동적으로 운영. 작성 2026-06-19 · 계기: 장수 워커의 메모리/스레드 누수 근본 제거
한 줄. 워커 프로세스를 오래 살리며 그 안에서 AEDT를 재사용/재생성하던 모델이 누수 2종을 낳았다. 이를 버리고 컨테이너 1개 = 시뮬 1건 = 완전 종료로 바꾼다. AEDT·pyaedt가 컨테이너와 함께 태어나 죽으니 누수는 OS 회수로 구조적으로 사라진다. 잡당 서브 오케스트레이터가 컨테이너를 동적으로 띄우고(오버슈팅 허용) 중앙 제어기가 전체 동시 컨테이너 수를 밴드로 묶는다.

1. 왜 바꾸나 — 오늘 확정한 근본 원인

장수(長壽) 워커 프로세스가 수백 솔브를 돌며 그 안에서 AEDT 수명을 관리한다. 어느 방식이든 cruft가 쌓인다:

모드누수증상
AEDT warm 재사용 (reclaim)AEDT 메모리 — close_project가 점유 메모리를 OS에 반환 안 함(프로세스 종료 때만)~1.5h 뒤 메모리 압박 → geometry import 실패(project_name=None) → 손상세션 재사용 실패 폭주 → 동시 solve 급락
매 솔브 AEDT kill (1솔브=1AEDT, 오늘 시도)pyaedt gRPC 스레드 — AEDT를 SIGKILL하면 워커 안 gRPC 클라이언트 스레드가 고아로 잔존(py-spy로 워커당 519 스레드 확인)500 스레드가 GIL thrash → 솔브 스레드가 GIL을 못 잡음 → AEDT idle(0 CPU) → 완료 ~1/분, effective collapse

공통 뿌리: "장수 프로세스 + 그 안의 AEDT 수명관리". 둘 다 프로세스가 안 죽어 누적이 안 풀린다. 레버: AEDT 수명 = 컨테이너 수명을 일치시키고, 그 단위를 1솔브로 짧게. 컨테이너가 죽으면 enroot가 mount/PID/메모리/스레드/temp를 전부 회수 → 누수 0.

잡당 1 서브 오케스트레이터

  • SLURM 잡 1개 = 컨테이너가 아니라 오케스트레이터 1개가 뜬다(장수, 잡 수명 10h 유지).
  • sshd 1개 보유. 잡→gate / 로컬→gate ssh 포워딩으로 잡마다 다른 포트 할당 → 로컬 컨트롤플레인이 ssh -p portN로 각 잡 오케스트레이터에 직접 도달(제어·디버깅·라이브 접속).
  • 역할: 작업 pull, 컨테이너 동적 spawn/대기/회수, 결과 relay, permit 중계, 메트릭 보고.
  • 터널은 잡당 1개(9개)로 단순화 — 컨테이너마다 터널 열던 것 폐기.

단명 컨테이너 (1솔브=1컨테이너)

  • 무조건 시뮬 1건만 수행하고 완전히 종료. 슬롯 재사용·warm 재사용 없음.
  • 컨테이너가 pyaedt+AEDT를 온전히 보유하고 같이 죽는다 → 메모리/스레드/temp 전부 회수.
  • 수명: enroot create+start → AEDT 콜드스타트 → geometry build → solve → 결과 push → exit.
  • 오케스트레이터의 node-localhost로 통신(작업 받기·결과 보내기·permit) → 컨테이너는 자기 터널 불필요.

3. 규모 · 오버슈팅 · 제어

파라미터값의미
잡당 컨테이너 상한40오버슈팅 허용 ceiling(잡 1개가 최대 40 컨테이너 동시).
전체 평균 동시 컨테이너100~150중앙 제어기가 이 밴드로 수렴(= 목표 동시 솔브).
잡당 평균11~179잡 × 11~17 ≈ 100~150.
1컨테이너 = 1 AEDT = 1 desktop + (솔브중)1 solve 라이선스풀 550이라 150 동시도 여유(현재 desktop 120/550).

오버슈팅이 버퍼(nominal > effective)를 만든다

컨테이너 수명 중 solve 단계는 일부다(enroot+AEDT콜드스타트+geometry build는 비-solve). 그래서 동시 컨테이너 N개여도 실제 solve중(effective)은 그보다 적다. 오버슈팅으로 컨테이너를 목표보다 더 띄워 항상 일부가 solve 단계에 있게 하면 effective가 목표(100~150)에 붙는다. 이게 어제 제어기 설계("solve<100이면 더 띄워 nominal>effective")의 컨테이너판 구현이다.

제어기

  • 중앙 라이선스 피드백 제어기(keeper)는 elec_solve_hfss(실측 동시 solve)를 100~150 밴드로 본다(기존 그대로).
  • 제어 출력 = 각 잡 오케스트레이터에 "목표 컨테이너 수" 지령(또는 컨테이너 spawn permit). solve<target이면 오버슈팅 상향, >ceiling이면 신규 spawn 정지(기존 컨테이너는 자기 솔브 끝내고 자연 종료 → youngest-kill 불필요해짐).
  • spawn은 오케스트레이터가 로컬에서 즉시(SLURM 스케줄러 안 거침) → 빠른 가감.

4. 컨테이너 수명주기 (상태기계)

spawn ─► enroot create+start ─► AEDT 콜드스타트(grpc up) ─► 작업1건 수령
      ─► cadquery geometry build ─► STEP import ─► HFSS solve ─► 결과 push(오케스트레이터 경유)
      ─► AEDT 정상 종료 ─► 컨테이너 exit ─► enroot remove(잔재 0)
실패/타임아웃(backstop) ─► 그냥 exit(다음 컨테이너가 새로) — 손상 세션 재사용 자체가 불가능
누수 0 보장. 메모리 누수: 컨테이너 exit = AEDT 프로세스 종료 = OS가 전부 반환(close_project 무관). 스레드 누수: pyaedt gRPC 스레드도 프로세스와 함께 소멸 → 고아 없음. 세션 손상: 매번 새 컨테이너라 손상 누적·재사용 불가 → 폭주 원천 차단.

5. 작업 · 결과 · permit 흐름

  • 작업 분배: 오케스트레이터가 baseline seed(잡·epoch별 disjoint, 이미 구현된 seed epoch 재사용)와 우선순위 lease를 컨테이너에 1건씩 배급. cadquery 샘플링은 컨테이너 안에서(기존과 동일).
  • 결과 회수: 컨테이너 → 오케스트레이터(node-local) → 잡 터널 → gate → 로컬 ingest(7876). 컨테이너 죽기 전 push 보장.
  • permit: 컨테이너 solve 직전 오케스트레이터에 요청 → 오케스트레이터가 중앙 제어기(7879)에 중계. 단, 컨테이너 수 자체를 제어기가 조절하므로 per-solve permit은 단순화 가능(spawn 시점이 곧 admission).
  • 라이브 디버깅: sshd로 ssh -p portN 접속 → 오케스트레이터/컨테이너 내부 직접 관찰(오늘 py-spy 고생 해소).

6. 콜드스타트 비용 — 이 설계의 핵심 트레이드오프

컨테이너마다 enroot create+start + AEDT 콜드스타트가 든다(솔브당 1회). 이걸 오버슈팅+파이프라이닝으로 숨긴다: 일부 컨테이너가 solve 도는 동안 다른 컨테이너가 setup 중 → 정상상태에서 effective는 끊김 없이 유지. 측정·튜닝 포인트:

  • enroot create 비용: enroot create가 sqsh에서 매번 풀면 비쌈 → 이미지 캐시/공유 rootfs/–rw 오버레이로 create를 가볍게(노드별 1회 unpack 후 컨테이너는 가벼운 start만).
  • AEDT grpc 기동 시간 실측(현재 timeout 270s지만 실제는 더 짧음) → 오버슈팅 폭을 이 값에 맞춰 산정.
  • 1솔브 = (setup T + solve S). 동시 effective 100 유지에 필요한 컨테이너 ≈ 100 × (T+S)/S. T가 크면 오버슈팅·ceiling을 키워야.

7. 구현 단계

  1. 오케스트레이터 골격: 잡 안에서 도는 장수 프로세스. sshd 기동 + 잡→gate 포트 포워딩(잡 인덱스→포트 매핑). 로컬 컨트롤플레인이 포트로 접속 확인.
  2. 컨테이너 러너(1솔브): 기존 entrypoint를 "1건 처리 후 exit"로 축약(EDT_MAX_SIMS=1과 유사하나 슬롯/슈퍼바이저 제거). pyaedt 정상 종료 경로 보장.
  3. 오케스트레이터 ↔ 컨테이너 IPC: node-local(유닉스 소켓/로컬 HTTP)로 작업 배급·결과 수집·permit 중계.
  4. 제어기 연동: 제어기 출력 = 잡별 목표 컨테이너 수. 오케스트레이터가 그 수를 유지(spawn/대기). youngest-kill → "신규 spawn 정지"로 대체.
  5. enroot create 경량화: 노드별 rootfs 1회 준비 + 컨테이너별 –rw 오버레이로 start만(콜드스타트 최소화).
  6. 관측: 대시보드 컨테이너 탭을 "잡별 컨테이너 수·수명·상태"로. nominal(전체 컨테이너) vs effective(solve중) 버퍼 가시화.
  7. 롤아웃: 1잡으로 파일럿 → 9잡 확대. 기존 50슬롯 컨테이너와 토글 가능하게.

8. 리스크 · 오픈 이슈

항목고려
enroot create 오버헤드매 컨테이너 unpack은 치명적. 공유 rootfs+오버레이 또는 풀린 이미지 재사용 필수. 선결 과제.
콜드스타트로 effective 하락오버슈팅 폭·ceiling(40)이 setup 비율을 흡수하도록 산정. 실측 T로 보정.
sshd 보안/키잡 sshd는 gate 경유 로컬만 접근(BatchMode key). 외부 노출 금지.
오케스트레이터 단일점잡당 1 오케스트레이터가 죽으면 그 잡 전체 정지 → 자체 감시·재기동, 컨테이너 고아 회수 로직.
결과 유실컨테이너가 push 전에 죽으면 그 솔브 유실(at-most-once). 재탐색으로 흡수 OR push 확인 후 exit.
SLURM 잡 수명잡(오케스트레이터)은 10h 유지, 컨테이너만 단명. 잡 만료 재기동은 기존 로직 재사용.
라이선스 churn컨테이너=1솔브라 checkout/checkin이 솔브당 1회. 동시 100~150이라 rate는 과거 450-kill보다 낮음(문제 없을 것으로 추정, 측정).

9. 기대 효과

  • 메모리 누수 0 — 컨테이너 종료로 전량 회수.
  • 스레드 누수 0 — gRPC 스레드가 프로세스와 소멸.
  • 세션 손상 폭주 0 — 매번 새 컨테이너, 손상 재사용 불가.
  • 버퍼 복원 — 오버슈팅으로 nominal>effective 유지 → solve 100~150 안정.
  • 디버깅성 — 잡 sshd로 라이브 접속.
  • 단순화 — 터널 9개(잡당), 슬롯/슈퍼바이저 장수 상태 제거.
