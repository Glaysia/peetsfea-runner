프로젝트 갈아엎기 계획 — 산재한 모순·구조 실패

2026-06-24 세션 진단 종합. 매일 1개(≈10%)씩 골라 dev에서 최적화하기 위한 픽 리스트. 우선순위 P0 발산/사고 P1 효율손실 P2 견고성 P3 정리 · 크기 S 반나절 M 하루 L 며칠

핵심 관통 모순 (1줄 요약): 컨트롤러는 유효 AEDT(동시 솔브 수)를 지령으로 수렴시키는데, 실제 천장은 anshpc(HPC 라이선스, 900)와 노드 용량이다. 컨트롤러가 이 천장을 모른 채 지령(250)을 쫓아 과-spawn → 라이선스 고갈 → 솔브 실패 → 유효 AEDT 더 낮게 관측 → 더 spawn의 양의 피드백(발산)이 핵심 병. 이번 세션의 90% 실패(analyze 즉시 False)가 전부 여기서 나왔다. 아래 항목 대부분이 이 한 모순의 가지들이다.

A. 자원 제어 — 진짜 병목을 모르는 제어기 (최상위)

A1P0M 적분 컨트롤러가 라이선스/노드 천장을 모른다 (양의 피드백 발산)

증거 target_aedt=250인데 anshpc 900을 16코어 솔브 12개씩 먹어 ~75 동시가 천장. 유효 AEDT 77에서 정체, 명목(컨테이너) 106+로 계속 spawn. 30분 성공률 5%.

모순 err = target − 관측유효인데, 실패로 관측유효가 낮으면 err↑ → 더 spawn → 라이선스 더 고갈 → 더 실패. 음의 피드백이어야 할 게 양의 피드백.

제안 컨트롤러에 자원 천장 항 추가: n_total ≤ min(target, anshpc_free/hpc_per_solve, node_slots). lmstat의 anshpc 가용분(poller가 이미 봄)을 관측해 spawn 상한을 동적으로. 실패율이 임계 초과면 spawn 동결(anti-windup).
A2P0S SOLVE_CORES ↔ 동시성이 암묵 결합 (모델에 없음)

증거 16코어=12 anshpc/솔브 → 최대 ~75 동시. 6코어=2 → ~450. 0.3.9.1에서 코어 16으로 올리며 동시성 천장이 1/6로 떨어진 걸 아무도 모델 안 함 → 0.3.9.5(6코어)까지 4번 버전 돌고서야 발견.

제안 max_concurrent_solve = anshpc_pool / max(1, SOLVE_CORES−HPC_FREE_CORES)를 명시 상수/계산으로 박고, target_aedt를 이 값으로 자동 clamp. 코어수 바꾸면 동시성 천장이 따라 바뀌게.
A3P1S wait_for_license가 데스크톱만, 솔버 HPC는 안 막음

증거 0.3.9.5 wait_for_license=True = 데스크톱 -waitforlicense만. analyze(HFSS HPC 솔버)는 anshpc 없으면 그냥 False. → 여전히 즉시 실패.

제안 솔버 단계 anshpc 대기/큐 방법 조사(ANSYSLI_TIMEOUT 등 라이선스 인터커넥트 대기 변수, batch solve 옵션) + peetsfea의 analyze 래퍼에 라이선스-실패 재시도(대기 후 retry) 추가. [세션 중 조사 미완 — 이어서]
A4P2M 두 제어 루프 + 방금 추가한 로드밸런싱의 상호작용 미검증

증거 잡(고정 인프라) + 컨테이너 N(적분) + 잡별 가중 재분배(distribute_weighted, 이번 세션 추가). 셋이 동시에 actuate. 가중 재분배가 적분 출력을 다시 쪼개 → 진동/편중 가능.

제안 제어 다이어그램 1장으로 정리(루프 주기·게인·상한) + 통합 시뮬/단위테스트로 안정성(진동·수렴) 검증. PLANS/integral_container_control.html 갱신.

B. 스케줄링 · 노드

B1P1S 잡 수(20) vs 노드 용량 불일치 → 만성 PENDING

증거 10잡/계정 × 2 = 20잡, 패킹 2/노드 + 계정분리 → 계정당 5노드 = 10노드 필요. cpu2 ~10노드를 타유저와 공유(mix 7/alloc 3) → hmlee31 2잡 상시 PENDING(Resources). 카운트 18에서 정체.

제안 잡 수를 노드 가용에 맞춰 동적으로(가용 노드×2/계정) 또는 줄여서 PENDING 제거. "고정 인프라"의 고정값을 클러스터 현실로.
B2P1S 노드 핀 경직 — ReqNodeNotAvail 고착

증거 런처가 --nodelist=n107로 핀 → n107이 빠지자 잡이 그 노드만 기다리며 PENDING 고착(694396).

제안 pending_reason()에서 ReqNodeNotAvail/Resources 장기 감지 시 avoid_node 등록 + scancel/재제출로 다른 노드 재라우팅(이미 avoid_node 인프라 있음 — 트리거만 연결).
B3P1S /enroot 포화 노드에 핀 → 가드 즉시종료 churn (20 찍자마자 하락)

증거 타유저가 채운 n113(free 43G<80G)에 잡이 떨어지면 orchestrator가 즉시 "스킵 종료" → 카운트 진동. 런처가 노드 선택 시 /enroot 여유를 안 봄.

제안 _candidate_nodes()에 /enroot 여유 사전필터(scontrol/df로 free<임계 노드 제외). 또는 가드 발동 노드를 avoid_node로.
B4P2M 계정간 노드 분리(peer_users)가 샌다

증거 n112·n114를 양 계정이 공유(겹침). squeue 반영지연 race + 노드부족으로 분리 회피가 깨짐.

제안 분리를 명시적 노드-셋 파티션(계정별 노드 풀 할당)으로, 또는 cross-account 예약을 control plane in-process 공유 상태로(squeue race 제거). private /dev/shm로 SHM 충돌은 막혀 치명적이진 않으니 P2.

C. 라이선스 · 오펀 누수

C1P1M teardown이 HPC 라이선스를 깨끗이 안 놓음 → linger로 풀 막힘

증거 버전전환마다 scancel한 16코어 솔브의 anshpc가 linger 상태로 648개(풀 72%) 잔류. lmremove 불가("Cannot remove a linger license"), 강제회수 권한/방법 없음. ~3시간 자연 timeout 대기.

제안 graceful teardown에서 ansysedt에 라이선스 release 신호(clean exit) 우선 + linger 기간 짧게 설정 가능한지(옵션파일/벤더) 조사. 최소한 버전전환을 잡 TTL 회전으로(scancel 대신) 해 linger 폭증 방지.
C2P3S orphan ansysedt/라이선스 모니터링·알람 부재

증거 우리 잡=0인데 라이선스 76 desktop·64 solve 잡힌 걸 수동 lmstat로야 발견.

제안 poller에 "내 잡 없는데 잡힌 라이선스(orphan)" 지표 + 대시보드 노출.

D. /dev/shm · 컨테이너 격리

D1P2S enroot가 host /dev/shm 공유 → KMP 오펀 오염 (패치됨, 근본은 남음)

증거 공유 /dev/shm에 stale __KMP_REGISTERED_LIB_*(타계정 소유) 누적 → hmlee31 ansysedt "Can't open SHM" abort(rc=134). 컨테이너별 private tmpfs /dev/shm 마운트로 임시패치.

제안 enroot 설정(hook/conf)에서 /dev/shm을 컨테이너 private로 기본화(orchestrator 인라인 mount 의존 제거). 노드 부팅 시 stale KMP 청소 cron도 고려.

E. 관측 · 대시보드

E1P2S 다계정 합산층이 임시방편 (merge 버그 다발) — 일부 수정됨

증거 _merge_histories 30s 버킷 과합산 → 추세 18→36/72 뻥튀기. _merge_snapshots 노드 통째 덮어쓰기 → n110 CPU 클로버. (둘 다 이번 세션 수정 8b4fac8.) 패턴: AggregatingResourceProvider가 급조됨.

제안 합산층 단위테스트 보강(다계정·오프셋 폴·노드 중복 케이스) + 라이선스 추세도 같은 carry-forward 일관 적용 검증.
E2P2M lmstat 파싱 / 계정별 poller fragility

증거 "hmlee31 poller license=None"(과거), lmstat 경로 하드코딩, 계정별 중복 폴, /status 엔드포인트 None 반환.

제안 lmstat 1회 폴을 공유(계정별 중복 제거), 파싱 견고화 + 실패 시 명시 에러, /status 스키마 점검.

F. 솔브 설정 · peetsfea 코드

F1P1L 솔브 설정이 움직이는 표적 — 정확도↔속도↔자원 trade-off 비체계

증거 0.3.9.0(지오메트리 3배 y-span) → 솔브 11→87분(8배). 0.3.8.3 skin-depth 메시 op 신설. 0.3.9.1~5에서 코어16→6, 메시 floor→fallback, pass 16/16/16, wait_for_license… 6번 버전을 더듬어 찾음.

제안 설계공간×메시×코어×라이선스를 묶은 1장 trade-off 모델/대시보드: "이 설정이면 솔브 X분·anshpc Y/솔브·동시 Z·정확도 W". 버전 바꿀 때 사전 예측되게. (PLANS/solve_time_30min_tuning.html 확장.)
F2P2M 남은 비-anshpc 실패 (실질 코드/지오메트리 버그)

증거 Raw Hfss.project_name must be str (NoneType) ×20, tx/rx_port edge_vertices 매칭 실패 ×11, SSW solve telemetry process did not stop ×9.

제안 각각 재현 + peetsfea 수정. project_name=None은 세션 생성 레이스/실패 처리, edge_vertices는 특정 지오메트리 엣지 매칭, telemetry는 정리 타임아웃.
F3P3S 16패스 강제(16/16/16)로 대부분 "수렴 안됨" 후 스윕

증거 batch.log "Adaptive Passes did not converge" → 그래도 스윕 진행. min=conv=max=16이라 사실상 16패스 고정·수렴요구 빡셈.

제안 수렴기준(delta_S)·패스수를 설계점 난이도에 맞춰. 정확도 가드(F1과 연계)로 수렴-미수렴 결과 품질 차이 측정.

G. 배포 · 환경

G1P2M pyproject 의존성 불완전 (재현 안 됨)

증거 venv 재생성 시 psycopg·uvicorn[standard]·path·pytest 누락(수동설치였음). 서비스가 import 실패. requires-python ==3.12.* vs peetsfea ==3.12.12 uv 해석 충돌.

제안 런타임/dev 의존성 전부 pyproject에 선언(psycopg[binary], uvicorn[standard], path…). requires-python을 peetsfea와 정합(==3.12.12). uv.lock 커밋해 재현 고정.
G2P2M 배포 토폴로지 ad-hoc (게이트 bare 레포·venv 산재)

증거 게이트별 ~/git/peetsfea.git bare 레포, canonical을 harry261 홈에(공유친화 umask 의존), venv 3개 수동 동기화, 두 게이트=같은 PC인데 별도 취급한 흔적.

제안 배포를 한 스크립트/문서로 표준화(git push → checkout → venv 동기화). "같은 PC + /gpfs 공유" 전제를 명시하고 canonical 위치·권한을 문서화. [세션 중 절반 정리됨]
G3P3S DB 단일 + 역터널 의존 (SPOF)

증거 결과가 역터널로 로컬 단일 PG에 push. web 재시작 시 ingest/터널 잠깐 끊김.

제안 ingest 재시도/버퍼링 견고화(이미 일부), 단일 DB 백업/복구 루틴 정례화.
