패치 계획 — 런타임 스크래치 /enroot 통합 미구현 · dev 전용

상태: 설계만 · 작성 2026-06-18 · 개정(reclaim-중심 → 근본-중심) · 형제 enroot_db_tracking.html · 구현·배포 안 함
한 줄. 문제의 근본은 "강제킬 때 안 지움"이 아니라 그 전에 — remote_job.py 경로가 런타임 루트를 /tmp로 잡고, 잡(워커)마다 2.7G 컨테이너 rootfs를 그 안에 새로 풀어서다. 근본 런타임 루트·rootfs·소켓을 /enroot/${USER}_${JOB} 밑으로 옮기고 unpack을 잡당 1회 공유로 바꾸면(=이미 slot_service.sh가 하는 방식), /tmp에 아무것도 안 생기고 매잡 2.7G 처닝도 사라지며 청소 로직이 하나(/enroot)로 일원화된다. 백스톱 그래도 남는 강제킬 고아는 기존 /enroot 시작-reclaim이 그대로 커버.

1. 문제 (근본 원인)

오늘 수동으로 34G 회수한 /tmp/$USER/peetsfea-runner/_runtime/pull.<jobid>.*(개당 2.7G)는 두 설계 선택의 결과 — "정상 종료 청소"는 이미 있고(trap), 누적은 강제킬 때만이지만, 애초에 그게 /tmp에 매잡 새로 생기는 것 자체가 불필요하다:

설계 선택지금 (remote_job.py 경로)코드
런타임 루트/tmp/$USER/peetsfea-runnerruntime_policy.py:7 REMOTE_COMPUTE_ROOT
워크dir 생성컨테이너보다 먼저 mktemp -d .../pull.<jobid>remote_job.py:3670

※ enroot은 .sqsh를 직접 못 돌리고 rootfs로 unpack해야 함 → "2.7G 존재"는 컨테이너 실행에 필요. 하지만 매잡·/tmp·새로 풀 필요는 없다.

대조군: slot_service.sh는 이미 옳게 함

2. 근본 픽스 근본

2.A 런타임 루트·rootfs·소켓을 /enroot 밑으로

  • REMOTE_COMPUTE_ROOT를 /tmp/$USER/peetsfea-runner → /enroot/${USER}_${SLURM_JOB_ID}(또는 그 하위)로. 워크dir·job_disk·rootfs가 전부 /enroot로 이동.
  • 소켓 PEETS_TUNNEL_SOCKET을 /tmp/peets-cp-* → $JOBDIR/cp.sock로(예 /enroot/1468_682631/cp.sock, ~28자 → unix 소켓 108자 한도 무관).
  • 효과: 기존 /enroot 청소가 전부 커버 → 추가 /tmp 전용 reclaim 불필요, /tmp 잔재 0.

2.B unpack을 잡당 1회 공유로 (워커별 → 잡별)

  • 지금은 enroot_base=…/worker-$$로 워커마다 rootfs를 풂 → 2.7G가 워커수만큼 중복.
  • slot_service.sh처럼 잡당 컨테이너 1개(edt-job-$JOB)를 만들고 워커들이 그 안의 프로세스로 공유 → 노드당 2.7G 한 번.

2.C [권장 대안] remote_job.py /tmp 경로를 slot_service.sh 모델로 통합/폐기

2.A+2.B는 결국 slot_service.sh가 이미 구현한 것이다. 두 경로가 병존할 이유가 없다면, remote_job.py의 /tmp-pull 경로를 slot_service.sh 모델로 흡수하거나 폐기하는 게 가장 깔끔. → 선결: 둘 중 현재 프로덕션 경로가 무엇인지 확정 필요(keeper가 sbatch하는 것). 잔재 jobid가 6월이라 최근까지 /tmp-pull도 돌았을 수 있음.

2.D [스트레치] 노드당 1회 unpack 공유

잡당 1회(2.B)에서 더 나아가 노드당 1회 풀어 read-only 공유 + 워커별 작은 오버레이면 반복 unpack 자체가 사라짐. 단 rootless overlay 공유는 subuid가 필요한데 이 클러스터 컴퓨트노드는 subuid가 빠져 있어(별도 확인됨) 당장은 비용이 큼. 2.B(잡당 1회)가 현실적 목표.

3. 백스톱 — 강제킬 고아 회수 백스톱

2.A로 모든 잔재가 /enroot/${USER}_* 밑으로 가면, 기존 slot_service 시작-reclaim(26-39줄: squeue에 없는 /enroot/${USER}_* 통째 rm -rf)이 강제킬 고아까지 자동 커버 — 거의 공짜. 추가로 챙길 것:

  • 소켓을 $JOBDIR/cp.sock로 옮기면(2.A) rm -rf $JOBDIR 한 방에 같이 삭제 → 별도 소켓 reclaim 불필요.
  • (개정 전 계획의 3.1 (c)(d) 케이스는 불필요해짐) — 잔재가 /tmp에 안 생기므로 /tmp 전용 reclaim 로직을 새로 안 짜도 됨. 즉 "닦는 로직 추가"가 아니라 "샐 곳을 없애" 청소를 단일화.
  • 무용한 gate-측 TTL 자니터(cleanup_orphan_sessions_for_run, 587-616; config.host=gate라 노드로컬에 안 닿음)는 폐기.
  • idle 노드(재사용 안 돼 reclaim 안 도는) 사각지대는 enroot_db_tracking.html(중앙 가시성)로 보완.

5. 안전성 / 테스트 / 롤아웃

  • 안전: /enroot 시작-reclaim은 squeue 실패 시 스킵(live 잡 보호) + ${USER}_ prefix 스코프 — 기존 검증된 가드 그대로 상속.
  • 용량: /enroot는 노드로컬·대용량(slot_service 주석). 2.7G/잡 수용 OK, /tmp(작을 수 있음) 압박 해소.
  • 테스트: ① 잡 정상 종료 후 /enroot/${USER}_$JOB 0 ② scancel -s KILL로 고아 생성 → 같은 노드 새 잡 시작로그 cleaning stale /enroot + 회수 확인 ③ /tmp에 harry261 잔재 0(루트·소켓) ④ live 잡 보존 회귀.
  • 롤아웃: remote_job.py(루트·소켓·unpack 위치) + 필요 시 runtime_policy.py 변경 → 컨테이너 동봉 slot_service.sh면 재배포(keeper 재시작). 단계: 2.A → 2.B → (2.C 통합/폐기) → 3 정리.
  • 범위: 지금은 구현 안 함, dev 계획 문서로만. 오늘 34G는 수동 회수 완료 → 이 패치는 재발·낭비 영구 차단.
