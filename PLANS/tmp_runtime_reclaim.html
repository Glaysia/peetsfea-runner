패치 계획 — /tmp 런타임 잔재 자동회수 미구현 · dev 전용

상태: 설계만 · 작성 2026-06-18 · 형제 문서 enroot_db_tracking.html(중앙 가시성) · 구현·배포 안 함
한 줄. 강제킬(SIGKILL/OOM/노드크래시)로 trap을 못 탄 잡이 남긴 /tmp/$USER/peetsfea-runner/_runtime/pull.<jobid>.*(개당 2.7G)와 /tmp/peets-cp-<jobid>-*.sock을, 이미 잘 도는 slot_service 시작-청소(squeue 기반 고아회수)에 2줄 추가해서 자동 회수한다. 오늘 수동으로 34G 지운 그 잔재의 영구 해결.

1. 문제

오늘 28노드에서 회수한 잔재의 정체(전부 harry261 소유):

유형경로생성 주체크기
워크dir/tmp/$USER/peetsfea-runner/_runtime/pull.<jobid>.XXXXXX/잡 스크립트 mktemp -d2.7G/개 (n109 22G·n110 6.6G·n112 4.9G)
터널 소켓/tmp/peets-cp-<jobid>-<port>-<pid>.sock잡 스크립트 ssh control-master0바이트(개수만)

※ AEDT 임시(pyaedt 로그·.pjt·file*)는 이미 TMPDIR 리다이렉트로 워크dir 안에 들어가므로 워크dir만 지우면 같이 회수됨. AnsysEM.mw.<user>는 노드당 1개·비누적이라 범위 외.

2. 근본 원인 (코드 앵커)

  • 워크dir 생성: remote_job.py:3670 mktemp -d "$REMOTE_RUNTIME_ROOT/pull.${SLURM_JOB_ID}.XXXXXX".
  • 정상 종료 청소는 있음: remote_job.py:3680-3691 trap cleanup EXIT → cleanup_workdir()=rm -rf $workdir. → 그러나 SIGKILL/OOM/노드크래시 땐 trap을 못 타 워크dir 통째 고아.
  • 소켓은 정상 종료에도 샐 수 있음: remote_job.py:3714의 /tmp/peets-cp-*.sock은 workdir 밖이라 cleanup_workdir가 안 지움.
  • TTL 자니터가 엉뚱한 호스트에서 돈다: cleanup_orphan_sessions_for_run(remote_job.py:587-616)은 runtime_root의 오래된 dir을 rm하지만 _ssh_command(config, config.host, …) 즉 gate에서 실행됨. 잔재는 컴퓨트노드 로컬 /tmp라 영영 안 닿음. (게다가 순수 -mmin 기반이라 live 잡 보호도 없음.)
  • 시작-청소는 /enroot만: slot_service.sh:24-37은 컴퓨트노드에서 squeue로 죽은 잡 jobid를 구해 /enroot/${USER}_* 스크래치와 edt-job-* 컨테이너를 회수한다 — 근데 /tmp/$USER/peetsfea-runner/_runtime/pull.*·소켓은 대상에서 빠져 있음.

3. 픽스 (최소·검증된 메커니즘 재사용)

3.1 (주) slot_service 시작-청소에 (c)·(d) 추가

이미 도는 slot_service.sh:24-37 블록(squeue 기반·prefix 스코프·멱등·squeue 실패 시 스킵)에 두 케이스만 덧붙인다:

RUNNING_JIDS=$(squeue -h -u "$USER" -o "%i" 2>/dev/null)
if [ -n "$RUNNING_JIDS" ]; then          # 실패 시 스킵 = live 잡 오삭제 방지(기존 안전장치)
  ...(a) /enroot/${USER}_* 스크래치  ...(b) edt-job-* 컨테이너  [기존]

  # (c) /tmp 런타임 워크dir 잔재 — 죽은 잡의 pull.<jobid>.*
  for d in /tmp/${USER}/peetsfea-runner/_runtime/pull.*; do
    [ -d "$d" ] || continue
    jid=$(basename "$d" | sed -E 's/pull\.([0-9]+)\..*/\1/')
    echo "$RUNNING_JIDS" | grep -qx "$jid" || { echo "[slot] cleaning stale runtime: $d"; rm -rf "$d" 2>/dev/null || true; }
  done

  # (d) 컨트롤플레인 터널 소켓 잔재 — 죽은 잡의 peets-cp-<jobid>-*.sock
  for s in /tmp/peets-cp-*.sock; do
    [ -e "$s" ] || continue
    jid=$(basename "$s" | sed -E 's/peets-cp-([0-9]+)-.*/\1/')
    echo "$RUNNING_JIDS" | grep -qx "$jid" || { echo "[slot] cleaning stale sock: $s"; rm -f "$s" 2>/dev/null || true; }
  done
fi

소켓은 find -user $USER 대신 peets-cp- prefix라 우리 것만 매칭. jobid가 squeue에 살아있으면 보존.

3.2 (부) 정상 종료 경로도 소켓 청소

remote_job.py의 cleanup_workdir()(3680)에 rm -f "$PEETS_TUNNEL_SOCKET" 한 줄 추가 → graceful 종료에서도 소켓이 안 남게(3.1의 (d)는 강제킬 백스톱).

3.3 (선택) TTL 자니터 호스트 수정 또는 폐기

cleanup_orphan_sessions_for_run은 gate에서 도느라 무용 → (i) 컴퓨트노드 타깃으로 고치거나, (ii) 3.1이 노드-로컬을 덮으므로 그냥 폐기(권장). 다만 3.1은 그 노드에 새 잡이 떠야 도는 한계가 있어, 재사용 안 되는 idle 노드 잔재는 못 잡음 → 중앙 가시성은 enroot_db_tracking.html(생성/삭제 DB 기록)로 보완.

4. 안전성

  • squeue 실패 → 전체 스킵(기존 가드 그대로): live 잡 dir 오삭제 0.
  • 스코프 한정: /tmp/$USER/...·peets-cp- prefix·jobid 매칭 → 남의 파일/시스템 파일 안 건드림(오늘 수동청소와 동일 원칙).
  • 멱등: rm -rf 반복 무해.
  • live 보호: jobid가 squeue에 있으면 보존 → 돌고 있는 잡의 워크dir·소켓 안전.

5. 테스트 / 검증

  • 단위: jobid 파싱 정규식(pull.<jobid>., peets-cp-<jobid>-) 케이스, squeue-빈값 스킵.
  • 통합: 잡 하나 scancel -s KILL(트랩 우회)로 죽여 잔재 생성 → 같은 노드에 새 잡 → 시작로그에 cleaning stale runtime/sock + find /tmp -user $USER 0 확인.
  • 회귀: 돌고 있는 잡의 pull.<live>·소켓이 보존되는지(오삭제 0).

6. 롤아웃 / 범위

  • slot_service.sh는 컨테이너 동봉 → 컨테이너 재배포(keeper 재시작) 필요. remote_job.py 변경분도 같이.
  • 지금은 구현 안 함 — dev 브랜치 계획 문서로만. 승인 시 3.1→3.2→(3.3 폐기) 순 패치 + 테스트 + 재배포.
  • 오늘 이미 수동으로 34G 회수 완료 → 이 패치는 재발 방지(영구 자동화)가 목적.
