2. 8080 시계열 대시보드 — x축=시간 (설계 + 실데이터)

현재 :8080은 순간 스냅샷만 보여준다(지금 부하·누적 카운트). 운영 추세를 보려면 x축을 시간으로 둔 시계열이 필요하다. 아래는 실측 데이터로 그린 차트와, 각 패널의 데이터 출처/구현 방법(0.3.7 소스 작업)이다.

① 처리량 / 성공·실패 (실데이터, 15분 버킷)

성공실패GPU 사용(성공 중)

실측 33버킷. 18:00·19:00의 실패 급증은 램프업/구 백스톱(98분) 타임아웃 버스트 → 백스톱 150분 상향 후 21:00~22:45 거의 성공만(21:30 피크 성공22/GPU12). 출처: DB finished_at를 서버측 time_bucket 집계 → GET /api/timeseries?metric=throughput&bucket=15m.

② 자원 시계열 — CPU / GPU / RAM 0.3.7 구현

샘플 형태(실데이터 아님 — 자원은 현재 순간값만 캐시). 구현: ResourcePoller가 지금은 순간 스냅샷만 → 시간순 링버퍼(최근 24h, 메모리)에 누적 → GET /api/resources/history?metric=cpuload|gpu_util|mem. 노드별 CPULoad(잡 할당코어 분모), GPU util(nvidia-smi), RAM 사용.

③ 입력 큐 · 동시 솔브 · 라이선스 0.3.7 구현

샘플 형태. 입력 큐 깊이(baseline/우선순위 레인 길이) + 동시 running 솔브 수 + electronics_desktop 라이선스 사용을 한 시간축에. 출처: TwoLaneQueue 길이 스냅샷 + squeue running + lmstat — 모두 링버퍼에 누적.

구현 메모 (0.3.7, 소스 작업 — 지금은 설계만)

  • 결과 시계열: 추가 저장 불필요. 이미 있는 finished_at/solve_telemetry를 DuckDB time_bucket으로 서버측 집계 → /api/timeseries(전체 행 비전송).
  • 자원 시계열: ResourcePoller에 시간순 링버퍼 추가(20s 간격, 최근 24h ≈ 4320포인트, 경량). → /api/resources/history.
  • 프론트: "추세" 탭 신설 — 시간축 라인/스택 차트(기존 SVG 렌더러 재사용, 자동 새로고침). 본 HTML의 렌더 함수가 그 프로토타입.
  • 활용: 처리량 급락=장애 감지, 라이선스 포화 경보, GPU/CPU 효과의 시간적 안정성(자동 벤치마크).

3. 0.3.7 패치 계획

효과: BackstopTimeout(실패의 30%) 소멸 + 처리량 ~2배(워커 회전 빨라짐) + cpu2 실패율 급감. 단, 메시↓로 정밀도는 일부 trade-off — 수렴/포트 품질 모니터 필요.

권고 mesh 외 추가 패치 (실패의 ~60%)

  • ① 포트 엣지 매칭 (34%, 최다) — peetsfea RX 포트-엣지 매칭에 허용오차/재시도/우아한 스킵. 수율 1순위 레버. (0.3.7 mesh로 안 잡힘)
  • ② pyaedt project_name=None 충돌 (22%) — process-per-slot 격리의 레이스(워커 재기동·grpc 포트 충돌) 조사. 재시도 시 collision-safe project 이름.
  • ③ FileExistsError — 재탐색 시 기존 출력 디렉토리 덮어쓰기/스킵.
  • ④ 0.25um? — MESH_MAX_LENGTH=0.25um(RestrictLength=True)은 0.25mm 오타 의심. ill-conditioned mesh 유발 가능 — 0.3.7에서 확인 권장.

①+②만 잡아도 실패의 56%가 추가로 줄어든다. mesh 완화(30%)와 합치면 성공률이 크게 오를 여지.
