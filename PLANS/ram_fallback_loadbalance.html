계획 — CPU 포화 시 RAM-여유 노드 우선 admission 미구현 · dev 전용

작성 2026-06-18 · 계기: "모든 노드 CPU 100%면 RAM 낮은(여유 많은) 노드로 다음 작업" 동작 부재 확인 · 구현·배포 안 함
한 줄. 지금 admission은 로컬 하드 CPU/mem 게이트(85%)라, 모든 노드 CPU가 포화되면 전부 보류 → 완전 정지한다. 여기에 "CPU 포화 시 RAM 여유가 가장 많은 노드부터 다음 솔브를 허용"하는 중앙 폴백 티어를 추가해, 멈추는 대신 RAM 헤드룸을 활용해 throughput을 흘린다.

1. 현재 상태 (확인 결과)

디스패처 admission은 2-게이트(edt_dispatcher.py:_await_admission):

  • ① 라이선스 permit — 전역 동시솔브 밴드(target~ceiling, 라이선스 제어기). 중앙.
  • ② 로컬 CPU/mem 게이트 — AdmissionController.can_admit()(edt_load.py). psutil로 자기 노드만 측정해 CPU≥85% OR mem≥85%면 False. 각 노드 독립, 전역 시야 없음. (코드 주석: "CPU는 로컬 로드밸런싱".)
상황현재 동작
일부 노드 CPU 여유그 노드들이 솔브 admit → 자연 분산(의도대로)
모든 노드 CPU≥85%모든 노드 can_admit()=False → 전 admission 정지. RAM 여유 무관.

즉 RAM은 CPU와 대칭 하드 게이트(85%)일 뿐, "CPU 포화 시 RAM 낮은 노드 우선"이라는 폴백/우선순위는 없다.

2. 목표 동작

  • 평상시: 지금처럼 CPU 여유 노드에 분산(변경 없음).
  • 모든(우리) 노드 CPU 포화 시: 멈추지 말고, FreeMem이 가장 큰(=RAM 사용 낮은) 노드부터 다음 솔브를 소수 허용. RAM 헤드룸이 있는 노드가 "한 건 더"를 받게.
  • 이유: HFSS 솔브는 후반 RAM-바운드가 많아, CPU가 명목 포화여도 RAM 여유 노드는 1건 더 수용 가능. 전면 정지보다 throughput 유지.

3. 설계 (중앙 시야 활용)

로컬 게이트만으론 "노드 간 RAM 우선순위"가 불가(노드가 남의 RAM을 모름). 이미 있는 중앙 컴포넌트를 쓴다:

  • 자원 폴러(이제 keeper/control측): scontrol로 노드별 CPULoad·FreeMem를 이미 수집(snapshot()["nodes"]).
  • permit 제어기(중앙): 워커가 솔브 직전 permit.acquire(). worker_id에 host가 인코딩됨(j{jidx}-w{widx}-{host}-{pid}).

3.1 RAM-폴백 티어를 permit 제어기에

permit(worker_id):
  node = host_of(worker_id)
  nodes = poller.snapshot()["nodes"]            # 노드별 CPULoad·FreeMem·cputot
  cpu_saturated_all = all(load/cputot >= CPU_SAT for n in our_nodes)
  if not cpu_saturated_all:
     return <기존 밴드 로직>                     # 평상시: CPU 여유 노드가 로컬 게이트로 알아서
  # CPU 전면 포화 → RAM-우선 폴백:
  rank = sort(our_nodes, key=FreeMem desc)       # RAM 여유 큰 노드 우선
  allow = node in top-K by FreeMem AND FreeMem >= RAM_FLOOR_MB
  return allow (소수 동시 한도 RAM_FALLBACK_CONCURRENCY 내)
  • 로컬 게이트 완화 연동: CPU 포화 폴백일 때, 디스패처가 로컬 can_admit()의 CPU 조건을 우회(또는 AdmissionController에 cpu_bypass_when_ram_ok 플래그)하되 mem 하드가드(예 mem≥90%)는 유지 — OOM 방지.
  • 소수 한도: RAM_FALLBACK_CONCURRENCY(예 노드당 1~2)로 제한해 RAM-폴백이 CPU를 다시 thrash로 몰지 않게.

5. 고려사항

  • 0.3.7.1(4코어 핀) 이후 CPU 포화 자체가 드물어짐 → 이 폴백은 2차 안전밸브. 평상시 동작 불변.
  • OOM 가드 최우선: "RAM 낮은(여유 많은)"을 고를 때 FreeMem 큰 노드 우선 + RAM_FLOOR 하한. 절대 mem 포화 노드에 폴백 admit 금지.
  • 재-thrash 방지: 소수 한도 + 히스테리시스. 폴백이 다시 전 노드 CPU를 100으로 밀면 안 됨.
  • worker→node 매핑: worker_id의 host로. 폴러 노드키와 정규화(예 nib109↔n109) 필요할 수 있음.
  • 대안(단순·열위): 로컬만 — can_admit()에 "CPU 높아도 local mem 낮으면 throttled admit". 노드 간 우선순위는 없어 전 노드가 동시에 풀려 thrash 위험 → 중앙안 권장.

6. 범위

  • 미구현 — dev 계획 문서. 착수 시: edt_license_ctrl.permit에 RAM-폴백 티어 + 폴러 노드데이터 주입 + AdmissionController CPU우회/mem가드 + 파라미터/히스테리시스 + 테스트.
