계획서 — 라이선스 피드백 제어기

상태: 계획(미구현) · 작성 2026-06-17 · 대상 peetsfea-web(중앙 제어) + 컨테이너 워커(게이트) · main 배포·컨테이너 사이클 동반
목표. 지금 동시 라이선스가 ~20개만 돌아 클러스터가 놀고 있다. 이 제어기의 핵심 이유: 슬롯을 450개(50×9) 열어둬도 실제 동시 솔브는 ~100밖에 안 될 수 있어, 그 수를 능동적으로 목표 100에 맞춰 올리고 묶는다. 100 미만이면 솔브를 더 시작, 150 초과면 가장 최근 시작한 솔브를 끈다 → 수렴값이 매 시간 100~150 안에. 솔브 안 도는 idle AEDT는 CPU·라이선스를 안 먹으므로 슬롯은 여유롭게 열어둬도 된다. 솔브가 ~14분짜리라 동역학이 느려서 폴링은 1분이면 충분.

1. 요구사항 (그대로)

요구설계 반영
로드밸런싱은 그대로(CPU 여유로운 데 admit)워커 로컬 AdmissionController(CPU/mem AIMD) 유지 + 라이선스 게이트 추가
컨테이너당 최대 50, 여유롭게EDT_SLOT_COUNT 11→50. idle AEDT는 라이선스 안 먹음(50×9=450 OK)
제어 지령 = 라이선스 사용수 100중앙 제어기 TARGET=100. lic_mine < 100이면 permit 발급
폴링 주기 줄이기제어 루프·lic_mine 폴 1분(솔브 ~14분이라 충분)
150 초과 → 가장 적게 시뮬한 ansys 끔lic_mine > 150이면 in-flight 중 youngest(가장 최근 시작) 솔브 abort
<100 많이, >150 적게, 수렴 100~150permit(상한) + youngest-kill(하한 안전) 이중 피드백 → 밴드 수렴

2. 현재 구조 (왜 중앙 제어가 필요한가)

  • 컨테이너 = SLURM 잡 = supervisor → 워커 프로세스 N개(process-per-slot). 워커 1개 = SlotDispatcher 1슬롯 = AEDT 1개.
  • 현행 admission(edt_load.AdmissionController)은 워커마다 로컬 — 노드 CPU/mem watermark + AIMD. 전역 라이선스는 모른다.
  • 라이선스 사용수는 전역 신호(9컨테이너×슬롯 합산, lmstat). 솔브 시작 결정은 각 워커가 함 → 전역 카운트를 워커가 물어볼 중앙 권위가 필요.
  • 왜 20개만 도나(추정): 로컬 mem watermark admission이 보수적이라 솔브를 묶고 있음. 라이선스를 1차 신호로 올리면 ~100까지 열림.

3. 설계 — 중앙 라이선스 제어기

peetsfea-web 안에 제어기 + 슈퍼컴 전용 백채널 :7879(역터널, 7876/7878과 동일 토폴로지). 워커가 솔브 직전/도중에 질의.

3.1 신호와 상태

  • lic_mine: ResourcePoller가 lmstat로 폴링하는 내 라이선스 사용수(진실). 제어기는 1분 주기로 읽음(솔브 ~14분이라 충분). 측정 지연 있음.
  • active_permits: 제어기가 발급했고 아직 release 안 된 솔브 집합 {worker_id: (granted_at, last_seen)}. ≈ 내 실제 동시 솔브수.
  • effective = max(lic_mine, len(active_permits)): 측정 지연(lmstat 늦음)과 드리프트(lmstat가 높음) 양쪽에 안전하게 더 큰 값을 쓴다.

3.2 admission (상한 — 오버슈트 차단)

워커: 솔브 직전 → POST /permit {worker_id}
제어기: effective < TARGET(100) 이면  → {grant:true}, active_permits[worker]=now
                                   아니면 → {grant:false}  (워커는 backoff 후 재시도)
워커: 솔브 끝 → POST /release {worker_id}  → active_permits.pop(worker)
TTL: heartbeat 끊긴 permit은 만료 제거(워커 사망 등 누수 방지)
  • thundering-herd 차단이 핵심: 450 idle 슬롯이 동시에 lic_mine<100을 보고 우르르 시작하면 폴링 지연 때문에 한참 초과한다. active_permits를 같이 세서 발급 즉시 effective가 오르므로 중앙에서 원자적으로 100에 묶인다.
  • 그래서 lic_mine만이 아니라 max(lic_mine, 발급수)로 게이트.

3.3 youngest-kill (하한 안전 — 150 초과)

워커: 솔브 도중 주기 heartbeat → POST /heartbeat {worker_id, solve_started_at}
제어기: lic_mine > CEILING(150) 이면
   → in-flight 중 solve_started_at 최댓값(youngest) 워커를 abort 대상으로 표시
   → 그 워커의 다음 heartbeat 응답에 {abort:true}
   → 하나 끄고 재측정, 여전히 >150이면 다음 youngest (한 번에 하나씩)
워커: abort=true 받으면 현재 솔브 중단
  • youngest를 끄는 이유: 가장 최근 시작 = 가장 적게 진행 = 버리는 컴퓨트 최소(요구사항 그대로).
  • 드리프트/타 유저 급증으로 lmstat가 일시 초과해도 우리 쪽을 줄여 빠르게 150 아래로.

3.4 수렴 (왜 100~150에 드나)

  • permit 상한 100 → 평상시 발급은 100에서 멈춤 → in-flight ≈ 100 유지(솔브 끝나면 새로 발급, 다시 100). 수렴값 ≈ 100(밴드 하단).
  • 지연/herd로 일시 초과해도 effective 회계가 즉시 묶고, lmstat가 150을 넘기면 youngest-kill이 끌어내림. → 거의 항상 [100,150].
  • 밴드 폭(100→150)이 히스테리시스라 경계에서 진동(켰다 껐다)을 막는다.

4. 워커 측 변경

  • edt_dispatcher._await_admission: 기존 CPU admission 유지 + 라이선스 게이트 추가 → (CPU.can_admit() AND 제어기.permit()) 일 때만 솔브 시작.
  • 솔브 완료 후 /release. 솔브 도중 워커 watcher 스레드가 /heartbeat → abort 지령 수신.
  • 제어기 URL은 env EDT_LICENSE_CTRL_URL(슬롯서비스가 주입, lease와 동일 정터널 경유).

5. abort 메커니즘 위험

  • pyaedt 솔브는 executor에서 블로킹 C 콜이라 스레드 인터럽트로 깔끔히 못 끊는다. 현실적 abort:
  • 옵션 A(권장): 워커 프로세스 종료 → supervisor가 cold 재기동. youngest라 손실 적음. 단 AEDT cold-start 비용 + slot.backend.kill()로 /enroot·orphan 정리 필요(safe_scancel 백스톱).
  • 옵션 B: slot.backend.kill()만 호출(AEDT 죽임) 후 워커는 다음 루프 — pyaedt 상태가 깨질 수 있어 비권장.
  • 가드: abort는 드물어야 함(상한 회계가 평상시 막음). 분당 abort 횟수 상한 + 로그.

6. 슬롯 50 + 폴링 주의

  • EDT_SLOT_COUNT 50: 노드당 워커 50 → AEDT 50개 상주. 라이선스는 안 먹어도 RAM은 먹는다(idle AEDT도 수백 MB). 노드 768GB라 가능하나 측정 권장.
  • warm 전략: 현행은 슬롯 시작 시 ensure_warm(AEDT 미리 띄움). 50개를 다 warm하면 RAM·스폰 부담 → lazy warm(첫 솔브 직전 기동) 고려. 단 솔브당 cold-start 지연 추가.
  • 스태거: 50개를 180s 간격이면 2.5h. 줄여야(예 30~60s) 합리적 램프. 단 동시 AEDT cold-start 폭주 회피 균형 필요.
  • 제어 루프 1분(lmstat 1분 1회 — gate 부하 적음). 솔브가 느려 1분이면 충분.

8. 테스트

  • 제어기 단위: effective 회계(permit/release/TTL), TARGET 상한에서 grant 멈춤, lic>150에서 youngest 선택.
  • 오버슈트: 동시 N permit 요청에도 발급이 TARGET을 안 넘는지(herd 차단).
  • 수렴 시뮬: lic 신호를 fake로 주고 발급/abort가 100~150에 수렴하는지.
  • 워커 게이트: CPU admission AND permit 둘 다일 때만 솔브. abort 지령 시 중단 경로.

9. 롤아웃

  • 제어기/폴링/대시보드 = peetsfea-web 재시작.
  • 워커 게이트/슬롯50/스태거 = gate venv 동기 + keeper 재시작(잡 사이클). [[teardown-order-containers-first]] 순서.
  • 단계적 권장: ① admission(상한 100)만 먼저 → 라이선스 20→~100 확인 → ② youngest-kill(위험) 활성. (이번 계획서는 전체 설계, 구현 범위는 별도 합의)

10. 비목표 / 리스크

  • 타 유저 라이선스 비제어: issued 550, 우리 100~150이면 충분. 타 유저 급증으로 총 in_use가 차면 우리 grant가 자연 보류(effective↑) → 안전.
  • abort는 running 솔브를 죽이는 유일한 위험 지점 — 상한 회계로 평상시 발생 0에 가깝게, 발생 시 youngest라 손실 최소 + 로그.
  • 50 idle AEDT RAM·cold-start는 측정 후 lazy-warm/스태거로 조정.
  • 관련 후속: spill replay 미배선(blip 결과 유실)은 별개.
