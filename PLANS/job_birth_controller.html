제어 로직 — 2분 홀짝 잡 제어 루프 · 동시 솔브 100 수렴

컨테이너 1솔브=죽음 · squeue 최대 15 · 평균 RUNNING 9 + AEDT 120 목표 · 2026-06-19

1. 모델 한눈에

  • 컨테이너 = 1 솔브 = 죽음. 재가동(respawn) 없음 → 잡의 살아있는 컨테이너는 시간이 지나며 줄어든다(드레인).
  • 잡 = 출생 시 컨테이너 N개(≤20) 가동. 수명 최대 20분.
  • 제어 루프는 잡 수 구간을 보지 않는다. 2분마다 홀수/짝수 tick 행동을 번갈아 실행한다.
  • squeue 상한은 15개이며, 최근 목표는 평균 RUNNING 9개 + AEDT/solve 120개다.
  • PENDING 버퍼는 reason=None만 인정한다. PENDING 잡의 REASON이 빈값/None/null/(null)/pending이 아니면 즉시 stuck으로 보고 취소한다.
  • 목표: 동시 솔브 100에 수렴. 잡 제출은 노드별 균등 분산이 필요하다.

2. 제어 루프 (핵심) — 2분마다 홀짝 행동

매 2분→ 홀수 tick: 새 잡 4개 제출/ 짝수 tick: 가장 늙은 RUNNING 잡 1개 종료→ squeue 최대 15 
every poll:
    for job in pending_jobs:
        if pending_reason(job) not in {"", "None", "null", "(null)", "pending"}:
            cancel_pending_job(job)          # Priority/Resources/ReqNodeNotAvail 등은 즉시 제거
            avoid_node_if_known(job)

every 2 minutes:
    if squeue_count >= 15 and queue_is_stuck:
        stop_oldest_running_job()
        submit_jobs(1, spread="node-even")
        return

    if tick_number is odd:
        submit_jobs(4, spread="node-even", squeue_cap=15)
    else:
        stop_oldest_running_job()

target steady state:
    average RUNNING jobs ~= 9
    average AEDT/solve ~= 120
    squeue total <= 15
  • 잡 수 구간 없음: 램프/정상 단계를 나누지 않고 2분 tick의 홀짝만 본다.
  • 홀수 tick: 종료 없이 새 잡 4개만 요청한다. 후보 노드를 한쪽으로 몰지 않고 노드별로 균등 분산한다.
  • 짝수 tick: 제출 없이 현재 켜져 있는 RUNNING 잡 중 가장 오래된 잡 1개만 내린다.
  • PENDING 필터: REASON이 None 계열인 잡만 정상 대기열로 남긴다. Priority, Resources, ReqNodeNotAvail 등은 정상 버퍼가 아니므로 cap과 무관하게 바로 scancel한다.
  • stuck 회복: squeue가 15개로 꽉 찼는데 진행이 막히면 홀짝 규칙보다 우선해 가장 늙은 잡 1개를 내리고 추가 잡 1개만 요청한다.
  • 잡 수명 20분 = 하드 상한(그 전에 틱 교체/드레인되면 더 일찍 종료). 종료 시 AEDT·pyaedt·터널 소멸 → 누수 회수.
  • 새 잡마다 컨테이너 수 N은 출생 시 LUT(§3)로 결정.

3. N 결정 — LUT (잡 출생 시)

새 잡의 컨테이너 수 N은 현재 elec_solve_hfss 실측을 보고 계단형 LUT로 정한다. 낮을수록 세게 밀고, 150 근처에서는 잡당 10개까지 낮춘다.

solve = 현재 동시 솔브 수            # 실측 elec_solve_hfss (우리)

if   solve <=  90: N = 20
elif solve <= 100: N = 15
elif solve <= 110: N = 14
elif solve <= 120: N = 13
elif solve <= 130: N = 12
elif solve <= 140: N = 11
else             : N = 10

  • 0~90: 잡당 20개로 최대 밀기.
  • 100~150: 10 solve 증가마다 N을 1씩 낮춰 과한 출생을 줄인다.
  • 150 이상: 잡당 10개를 유지하고, 별도 포화 제어가 늙은 잡을 추가로 정리한다.

4. 포화 제어 — 12분마다 추가 감압

2분 제어 루프 여섯 번에 한 번(= 12분마다) 라이선스 사용량을 확인한다. elec_solve_hfss > 150이면 현재 켜져 있는 RUNNING 잡 중 가장 늙은 잡 1개를 추가로 종료한다. 
every sixth 2-minute tick:
    if license_solve_in_use > 150:
        stop_oldest_running_job()

5. 최근 2시간 관측 — 평균 9 jobs / AEDT 120으로 올리는 방법

목표는 평균 RUNNING job 9개와 평균 AEDT/solve license 120개다. 최근 2시간 (2026-06-19 16:54:35~18:54:20 KST, 307 samples) 관측상 잡당 license 효율은 충분하므로, 우선순위는 잡당 N 증가가 아니라 평균 RUNNING job 수를 올리는 것이다.

  • 진단: 현재 평균 AEDT 120을 못 찍는 이유는 job당 N이 낮아서가 아니라 RUNNING job 평균이 4~5개에 묶이기 때문이다.
  • 구현된 제약 완화: 런처는 node_based=True로 노드당 peetsfea job 1개만 허용하되, 기본 후보를 cpu2,gpu1,gpu2,gpu3로 넓힌다. 요청량은 cpu2 48 CPU + 480G, gpu 계열 24 CPU + 384G + gpu:1다.
  • 노드 관측: cpu2는 즉시 들어갈 수 있는 후보가 제한적이고, 기존 gpu1은 CPU가 남아도 gpu:2/480G 조건 때문에 PENDING/취소가 쉽게 생겼다. gpu2/gpu3에는 CPU와 메모리가 남은 MIX 노드가 여럿 보인다.
  • 1순위 조정 완료: 후보 파티션을 cpu2,gpu1에서 cpu2,gpu1,gpu2,gpu3까지 넓혔다. gpu4는 idle 노드가 보이면 보조 후보로만 둔다.
  • 2순위 조정 완료: gpu 파티션 요청을 gpu:2에서 gpu:1로 낮추고, cpus_other를 32에서 24로 낮춰 더 많은 MIX 노드에 백필되게 한다. GPU job 메모리는 384G로 낮춘다.
  • 3순위 조정 완료: 저수위 guard를 둔다. running_jobs < 9이면 짝수 tick의 oldest stop을 건너뛰고, 홀수 tick은 cap 15 안에서 보강 제출한다.
  • 유지: PENDING reason이 None 계열이 아니면 즉시 취소하는 정책은 유지한다. 평균 job 수를 올리는 1차 수단은 PENDING 완화가 아니라 후보 노드/자원 요청 확장이다.
target calculation:
    observed_aedt_per_running_job = 62.79 / 4.71 = 13.33~13.46
    target_aedt_per_running_job   = 120 / 9 = 13.33

therefore:
    keep N policy roughly as-is
    raise average RUNNING jobs from 4.7 to 9
    widen schedulable nodes
    reduce GPU job request size
    add low-water guard for RUNNING jobs < 9

6. herd 방지 (컨테이너 출생 stagger)

잡이 N개를 한꺼번에 켜면 그 노드에서 AEDT N개 동시 기동 → 방금 본 gRPC 행 재발. → orchestrator는 N개를 1개씩 간격 두고 가동(노드당 동시 콜드스타트 ≤ EDT_COLD_CAP=10).

7. 구현 포인트

레이어변경
제어기(루프)잡 수 구간을 보지 않고 2분마다 홀수 tick은 새 잡 4개 제출, 짝수 tick은 가장 늙은 잡 1개 종료. 단 RUNNING 9개 미만이면 짝수 tick 종료를 건너뛴다. squeue 총량은 15개로 제한한다. PENDING reason이 None 계열이 아니면 즉시 취소하고, cap 15에서 stuck이면 1개 종료 + 1개 요청.
orchestrator출생 시 N 받아 1솔브 컨테이너 N개 stagger 가동(respawn 없음). EDT_JOB_TTL_SEC=1200 또는 제어기 종료신호 시 진행 솔브 마치고 안전종료 → 잡 exit. /enroot 정리 trap 유지.
keeper노드별 균등 분산으로 제출하고, 평균 RUNNING 9 + AEDT/solve 120을 목표로 한다. 2분 tick 여섯 번마다 solve >150 포화 감압을 수행한다.
