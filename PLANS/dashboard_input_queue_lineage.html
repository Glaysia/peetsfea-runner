한 줄. 입력큐에서 몇 개 들어왔고 / 몇 개 돌고 있고 / 거기서 나온 출력이 몇 개인지를 대시보드에 추가한다. 컨테이너 워커 수정 0 — 결과의 request_id 접두사가 이미 출처를 담고 있어 DB(web)만으로 집계·연결 가능.

1. 가능 근거 (컨테이너 무수정)

request_id가 출처를 인코딩한다 — 별도 provenance 태그가 필요 없다:

출처request_id 형식코드
레퍼런스(baseline)base-{seed}-{i}edt_intake.py:80
입력큐(priority lease){sweep_request_id}-{seed}edt_priority_lease.py:133
정적 priority tomlprio-0edt_entrypoint.py:233
  • 입력큐 sweep은 priority_sweeps(request_id·seed·total_count·remaining_count·created_at)에 적재됨 — "들어온 수"의 원천.
  • 입력큐에서 나온 결과는 single_simulation_results.request_id LIKE '{sweep_request_id}-%' 로 prefix-join. request_id가 PK라 prefix 범위스캔 = 빠름.

2. 보여줄 지표

지표정의DB 출처
들어온 수입력큐로 제출된 후보 총수SUM(priority_sweeps.total_count)
대기(미분배)아직 lease 안 됨SUM(remaining_count)
분배됨(lease)워커가 당겨감SUM(total_count - remaining_count)
파생 출력(완료)입력큐에서 나온 결과(성공/실패)results prefix-join, terminal_state 집계
진행 중(추정)분배됐는데 아직 결과 없음분배됨 − 파생출력(완료) ≈ in-flight

3. 구현 (web/control-plane만)

3.1 store 메서드(신설)

def priority_lineage(self) -> dict:
    # 1) 입력큐 적재 현황
    SELECT count(*) sweeps, sum(total_count) submitted, sum(remaining_count) waiting
      FROM priority_sweeps
    # 2) sweep별 파생 결과(완료) — prefix-join
    SELECT ps.request_id, ps.total_count, ps.remaining_count,
           sum(CASE WHEN r.terminal_state='success' THEN 1 ELSE 0 END) ok,
           sum(CASE WHEN r.terminal_state='failed'  THEN 1 ELSE 0 END) fail
      FROM priority_sweeps ps
      LEFT JOIN single_simulation_results r
        ON r.request_id LIKE ps.request_id || '-%'
     GROUP BY ps.request_id, ps.total_count, ps.remaining_count
    # 집계: submitted / waiting / leased=submitted-waiting / done=ok+fail / inflight=leased-done

3.2 대시보드 엔드포인트 + UI

  • GET /api/queue/lineage → 위 집계 + sweep별 행.
  • 기존 입력큐 탭(이미 있음: /api/queue depth/items)에 카드 추가: 들어온 N · 대기 N · 진행 ~N · 파생출력 N(성공/실패) + sweep별 표(제출/대기/완료/진행).
  • (선택) 추세에 "입력큐 파생 처리량" 라인 추가.

4. 고려사항

  • 컨테이너 무수정 확정 — request_id 접두사가 출처를 담아 DB-only로 충분. 워커/슬롯서비스/이미지 안 건드림. (질문 답: 맞음)
  • 성능: prefix-join은 results.request_id(PK)의 범위스캔이라 sweep당 빠름. priority_sweeps는 소수 행. 11GB 결과 테이블에도 부담 적음(분리된 web 프로세스에서 실행).
  • "진행 중"은 추정치: 정확한 in-flight는 결과가 안 들어온 상태라 DB로 직접 못 셈 → (분배−완료)로 근사. 정확값이 필요하면 그때 별도(워커 heartbeat 등) 고려.
  • at-most-once lease: chunk 당긴 워커가 솔브 전 죽으면 그 분은 유실(remaining은 이미 차감) → "분배−완료"에 유실분이 섞일 수 있음. 표기로 명시.
  • prune 정합: 결과 7일 prune은 results, priority_sweeps는 별도 — 오래된 sweep의 파생 결과가 prune되면 done이 줄 수 있음(표기 주의).
