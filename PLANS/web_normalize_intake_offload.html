계획서 — web 정상화: 인테이크 분리 + results.csv 제거

상태: 계획(미구현) · 작성 2026-06-17 · 대상 peetsfea-web 프로세스 · 컨테이너 솔버 무관(일부 puller 변경만)
한 줄 요약. 무거운 cadquery 샘플링을 read-only 웹 프로세스에서 제거하고(인테이크는 sweep+개수만 받아 큐에 저장, 샘플링은 컨테이너가 baseline처럼 수행), /results.csv를 폐기하고 다운로드를 서버측 DuckDB COPY 기반 Parquet(추천)/jsonl/tar.zstd로 교체한다(CSV는 비효율·중복; 전 행 메모리 빌드도 제거). web 메모리 8~11GB → 1GB 미만 기대.

1. 문제

  • web 메모리 8~11GB — read-only 대시보드+백채널 서버 치고 비정상(정상은 수백MB~1GB). 어댑티브 버스트 때 14GB까지 폭증.
  • 근본 원인: 무거운 작업을 HTTP 요청 경로(web 프로세스)에 얹음.

1.1 인테이크가 web에서 geometry를 빌드한다

  • :7875/submit → IntakeService.submit → sample_fixed_candidates_from_toml_text(sweep, count, seed) 호출.
  • 이건 단순 N개 뽑기가 아니라 geometry 기반 rejection sampling — 후보마다 cadquery로 빌드해 불가능 설계를 걸러냄(~5s/후보, 수십 MB/후보).
  • ThreadingHTTPServer는 요청당 스레드를 무제한 생성 → 동시 cadquery 빌드가 쌓여 메모리 폭증.
  • 모순: baseline은 같은 샘플러를 컨테이너 안에서 돌린다(BaselineRefiller). 인테이크 경로만 잘못된 위치(web)에 있음.

1.2 /results.csv가 전 행을 web 메모리에 적재한다

  • /results.csv → rows_to_csv(fetch_rows(limit=None)) → 전 행 + 리포트 원문(csv_text_by_report_json)을 메모리에 통째 빌드.
  • CSV 자체가 비효율·중복 — 결과는 이미 DuckDB에 있고, 실데이터 소비/적재는 jsonl로 한다. CSV는 용량만 크고 쓰이지 않음.

2. 설계 A — 인테이크 분리 (샘플링을 컨테이너로)

인테이크를 "sweep toml + 개수"만 받는 얇은 큐잉으로. 무거운 샘플링은 솔브하는 곳(컨테이너)에서 — baseline과 대칭.

2.1 흐름

:7875/submit  (sweep_toml, count, seed)
   → 가벼운 검증만(range/schema, geometry 안 빌드) → priority_queue에 "sweep 요청" 1줄 저장 → 202 즉시
        row = (request_id, sweep_toml, seed, total_count, remaining_count, created_at)

워커(컨테이너; baseline과 동일 경로):
   PriorityPuller가 lease로 "이 sweep에서 k개" 받음  (remaining에서 k 차감 → 여러 워커에 분산)
   → 컨테이너 안에서 k개 cadquery 샘플링 (geometry 빌드 = 어차피 솔브 때 하는 일)
   → 로컬 우선순위 레인 적재 → 85:15 블렌드로 솔브 → 결과 ingest(:7876)

2.3 효과

  • web은 toml 문자열만 저장 → cadquery가 web에서 완전히 사라짐 → 메모리 폭증 원천 제거.
  • 무거운 geometry는 솔브하는 컨테이너에서 — 자연스럽고 baseline과 일관.
  • remaining 차감으로 한 sweep의 count가 여러 워커에 분산(한 워커 독점 방지).

2.4 주의 / 엣지

  • at-most-once: 워커가 chunk를 lease(remaining 차감)한 뒤 샘플/솔브 전에 죽으면 그 k개는 유실. 현행과 동일 수준이나 granularity가 chunk. 무손실 필요 시 lease-TTL/재배달(leased_at + 만료 복구)을 후속으로.
  • seed 분배: 워커가 받는 seed_base는 요청 seed + 이미 분배된 개수(=total-remaining)로 산출 → 후보 중복 방지.
  • 검증의 무게: validate_sweep_toml_text가 geometry를 안 빌드하는지 확인(빌드하면 그것도 컨테이너로). range/schema 체크만이면 web 유지 OK.

3. 설계 B — /results.csv 제거 + 다운로드 포맷 정비

  • 제거: /results.csv 엔드포인트, rows_to_csv(), 데이터셋 탭의 "전체 CSV 다운로드 ↓" 링크. 관련 테스트(test_csv_includes_full_output_dataset 등) 정리.
  • 이유: CSV는 비효율·중복 — 결과는 이미 DuckDB에 있고, 컬럼 늘면 헤더 폭증·타입 손실·용량만 큼.

3.1 다운로드 포맷 옵션 (전부 서버측 DuckDB COPY = web 메모리 적재 0)

핵심: rows_to_csv(fetch_rows(limit=None))처럼 전 행을 Python으로 빌드하지 말고, DuckDB가 파일로 직접 내보내고 그 파일을 스트리밍한다. 메모리 문제도 같이 해결.
포맷용도방식 / 비고
Parquet 추천ML/분석 데이터셋 적재(pandas·polars·duckdb)COPY (SELECT … WHERE peetsfea_version=?) TO 'x.parquet' (FORMAT PARQUET, COMPRESSION zstd). 컬럼형+zstd라 CSV/jsonl보다 작고 로드 빠름. 사실상 표준.
jsonl(NDJSON)사람이 읽기/스트림 처리읽기 좋지만 크고 느림. COPY … TO 'x.jsonl' (FORMAT JSON, ARRAY false) 또는 행 단위 yield. 압축 원하면 .jsonl.zst로 스트림.
tar.zstd압축 번들 다운로드(느린 jsonl 대안 / 원시 산출물)(a) Parquet/jsonl 결과 + (b) 선택한 sim들의 원시 per-sim 산출물(리포트 jsonl·곡선 등, 아카이브 batch_*.tar.gz 출처)을 tar | zstd로 묶어 스트리밍. 큰 다운로드는 압축이 사실상 필수.

3.2 엔드포인트(안)

  • GET /results.parquet?since=&peetsfea_version=&state= → DuckDB COPY … (FORMAT PARQUET, COMPRESSION zstd) → 임시파일 스트리밍 후 삭제.
  • GET /results.jsonl?… → 동일하되 JSON(스트리밍·선택적 zstd).
  • GET /export.tar.zst?ids=…|since=… → 결과 파일 + 원시 산출물 묶음을 zstd로 압축 스트리밍.
  • 전부 기본 필터/limit 적용(무한 풀스캔 방지) + 스트리밍(Content-Length 미리 안 잡고 chunked) → web 메모리 일정.
  • 의존성: zstd는 python-zstandard 또는 tar --zstd(시스템 zstd). DuckDB Parquet/JSON COPY는 내장.

4. 설계 C — (선택) 서버/폴링 부하

  • 요청당 스레드 무제한 완화: ThreadingHTTPServer에 워커 큐+세마포어, 또는 고정 워커풀 서버로. 인테이크 분리(A)만으로도 폭증은 잡히므로 우선순위 낮음.
  • lease 폴링 thundering herd: 워커 99개 ~2s 폴링(동시 49~127). 폴링 간격↑·배치↑, 또는 long-poll. A 적용 후 측정해서 결정.

6. 테스트

  • store: sweep 요청 enqueue / chunk lease(remaining 차감·0이면 삭제) / 동시 lease 분배 / 재시작 생존.
  • intake: submit이 geometry 안 빌드하고 sweep 1줄만 넣는지(샘플러 호출 0).
  • puller(컨테이너측): chunk 받아 k개 샘플 후 로컬 적재(fake 샘플러).
  • 대시보드: /results.csv 404(제거 확인) 또는 /results.jsonl 스트리밍. 입력큐 탭 remaining.
  • 회귀: 기존 스위트 통과 + 동시성 스모크(메모리 폭증 없음).

7. 롤아웃

  • web만 재시작으로 인테이크/CSV/대시보드 변경 반영(컨테이너 무관).
  • puller 변경은 컨테이너가 gate venv 코드를 쓰므로 gate venv 동기 + 잡 사이클 필요(keeper 재시작). [[teardown-order-containers-first]] 순서 준수.
  • 스키마 변경: 기존 priority_queue(후보 기반)는 비우거나 마이그레이션. 운영상 큐는 거의 비어 있어 드롭/재생성으로 충분.

8. 비목표 / 메모

  • 풀 분산(Redis/NATS 브로커, gunicorn 멀티프로세스)은 비목표 — 단일 노드·9잡·~100워커엔 과함. 인테이크 분리만으로 8GB→1GB 기대.
  • 관련 후속(별도): spilled 결과 미replay 배선(replay_spilled 미호출 → blip 시 결과 유실). 메모리와 별개지만 "데이터 안 새는 web" 묶음으로 같이 갈 수 있음.
  • 관련: resource_snapshots 7일 prune·우선순위 큐 DB 영속·DuckDB 동시 connect 크래시 수정은 이미 반영됨(이번 계획서 범위 밖).
