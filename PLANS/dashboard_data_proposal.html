영역현재문제
실패 기록 모든 envelope(success/failed/aborted)가 한 테이블 single_simulation_results에 영구 적재. 세션 중 누적된 failed 3,348건이 라이브 DB를 오염 → 쿼리·CSV가 노이즈 범벅, 성공 데이터셋이 묻힘, DB 비대화.
:8080 시각화 / 입출력 /(request_id·state·finished_at 테이블), /results.csv(in_*/tel_*/pass_*/reports_json 평탄화), /health. 차트·요약 없음. 입력 설계점↔출력 관계를 보거나 골라 얻기가 불편 — "입출력 파라미터 얻는거 아직도 안 됨". 리포트 곡선은 raw 텍스트뿐.
운영 정보 없음. psutil_load_sampler는 컨테이너 내부 admission 전용(노출·기록 안 됨). 자원 사용량·라이선스·잡 상태·파티션별 성능(GPU vs CPU)을 한 곳에서 못 본다. 자동 벤치마크 데이터는 쌓이는데 가시화가 없다.

제안 1  실패 기록 아카이브

목표: 라이브 DB는 가볍게(success + 최근 failed만), 과거 실패는 보존(추세 분석 가능)하되 라이브 쿼리에서 분리.

설계

  • 아카이브 싱크: 주기(기본 1h) 또는 임계(failed > N) 도달 시, terminal_state IN ('failed','aborted') 중 오래된 것을 Parquet로 덤프(edt-archive/results_failed/YYYYMMDD-HHMM.parquet, 시간 파티션) 후 라이브에서 DELETE.
  • 실패 요약은 라이브 유지: error_type별 카운트·최근 샘플은 요약 테이블(failure_summary)에 남겨, "어떤 실패가 많은지"는 대시보드에서 즉시 보이게(전체 레코드는 Parquet).
  • DuckDB 네이티브 활용: Parquet은 DuckDB가 직접 쿼리 가능 → SELECT error_type, count(*) FROM 'edt-archive/results_failed/*.parquet' GROUP BY 1 로 사후 분석.
  • 보존 정책: Parquet도 FIFO 상한(예: 50GB) — 기존 ArchiveStore FIFO 패턴 재사용.

효과

  • 라이브 DB가 success 중심으로 작아져 /results.csv·대시보드 쿼리가 빨라지고 노이즈 제거.
  • 실패는 사라지지 않고 Parquet으로 분석 가능 → 실패 모드 추세(예: 특정 설계점/파티션에서 실패율↑)를 자동 발견.

구현: edt_archive 옆에 edt_results_archive.py(덤프+삭제+요약), 컨트롤 플레인 poll 루프에 1h 틱 추가.

제안 2  :8080 시각화 & 입출력 데이터셋

목표: 입력 설계점 → 출력(리포트·지표)을 인터랙티브하게 보고 / 골라 내려받기. "입출력 파라미터 얻는거"를 정면 해결.

2-1. JSON API (edt_dashboard 확장, read-only)

엔드포인트반환
GET /api/summary누적·success·failed·aborted, 성공률, 평균/분포 solve 시간, GPU vs CPU 비율, 시간당 처리량.
GET /api/results?since=&state=&limit=&cols=입출력 데이터셋 행(JSON): in_*(입력) + tel_*·지표(출력) + 메타. 필터·페이지네이션.
GET /api/sim/<request_id>단일 시뮬 상세: 입력 파라미터 전체 + 출력 리포트 곡선(csv_text_by_report 파싱 → 플롯용 배열) + telemetry.
GET /api/design-space?x=&y=&c=산점도용 (입력 x, 입력 y, 색=결과/지표) 집계 — 설계공간 커버리지 시각화.
GET /results.csv(기존 유지) 전체 입출력 데이터셋 일괄 다운로드.

2-2. 프론트엔드 (정적 HTML+JS, :8080/ 서빙, Chart.js — 외부 의존 없이 단일 파일)

  • 요약 카드: 총/성공/실패, 성공률, 평균 solve 시간, 동시 solve, GPU vs CPU.
  • 입출력 테이블: 정렬·필터·검색, 입력(in_*) + 출력 지표 열, 행 클릭 → 상세, 현재 필터 CSV 다운로드.
  • 차트:
    • 설계공간 커버리지 — 입력 파라미터 산점도(결과/지표로 색).
    • 입력→출력 관계 — 예: 코일 turn 수 vs 출력 지표(서로게이트 직관).
    • solve 시간 분포 · 적응 패스 수렴(pass counts).
    • GPU vs CPU · 파티션별 벤치마크 — solve 시간 × gpu_used × partition.
    • 시간당 처리량 · 라이선스 사용 추이(시계열).
  • 시뮬 상세 뷰: 입력 파라미터 표 + 출력 리포트(주파수 곡선) 플롯 — raw 텍스트 대신 그래프.

제안 3  운영 텔레메트리 (각종 정보)

목표: 자원·라이선스·잡·파티션 성능을 한 화면에. 자동 벤치마크(GPU vs CPU, 파티션별)를 가시화.

설계

  • 컨테이너 → 데몬 push: 각 슬롯 서비스가 노드 cpu%/mem%/동시 solve 수를 주기적으로 결과 백채널 옆(경량 /telemetry)으로 push. 이미 partition/node를 기록하므로 노드별 집계 가능.
  • 데몬측 폴링: 데몬이 ssh gate로 squeue(잡 running/pending)·lmstat(electronics_desktop 사용)를 주기 조회해 캐시.
  • 대시보드 통합(/api/resources): 노드별 CPU/mem, 동시 solve, 라이선스 사용/총량, 잡 상태, 파티션 분포.
  • 자동 벤치마크: 이미 캡처 중인 gpu_used·solver_cores·elapsed_ms·partition·node로 "파티션별 평균 solve 시간 / GPU 효과"를 집계 — 운영만 해도 데이터가 쌓여 자동 벤치마크.

부록 — 이미 캡처 중인 데이터 (구현 불필요, 활용만)

컬럼(저장됨)구분용도
point_values_json입력설계점(ferrite 위치비·코일 turn/twist/void 등) → in_*
csv_text_by_report_json출력리포트 곡선(S-param 등) → 상세 뷰 플롯 / reports_json
solve_telemetry_json출력gpu_used·gpu_device_name·solver_cores·elapsed_ms·peak_* → tel_* · 벤치마크
setup_pass_counts_json출력적응 패스 수렴 → pass_*

terminal_state · error_*메타success/failed/aborted · 실패 모드 분석(제안 1)

구현 우선순위

  1. 제안 1 실패 아카이브 — 낮은 노력, 라이브 DB 건강 즉효. (edt_results_archive + poll 1h 틱)
  2. 제안 2 /api JSON + 프론트엔드 — "입출력 얻는거 아직도 안 됨"을 직접 해결. (요약·테이블·다운로드 먼저 → 차트)
  3. 제안 3 운영 텔레메트리 — 자원/라이선스/벤치마크. (데몬 폴링 → 컨테이너 push)

모두 read-only로 시뮬에 무간섭. 데이터는 이미 다 있으므로 신규 캡처 없이 표출·아카이브 레이어만 추가하면 된다.
