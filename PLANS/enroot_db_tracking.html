향후 계획 — /enroot 생성/삭제 DB 기록 미구현 · dev 전용

상태: 아이디어/설계만 · 작성 2026-06-17 · 구현·배포 안 함, dev 브랜치 문서로만 보관
한 줄. 컨테이너가 /enroot에 스크래치 dir·enroot 컨테이너를 만들거나 지울 때마다 DB에 이벤트를 남겨, 어느 노드에 잔재가 떠 있는지(생성됐는데 삭제 안 됨)를 srun 없이 중앙에서 감사한다.

1. 문제 (왜)

  • /enroot/{USER}_{JOB} 스크래치 + edt-job-{JOB} enroot 컨테이너는 노드 로컬이라, 잔재를 보려면 노드마다 srun 점검이 필요 — 무겁고 사각지대(잡 안 뜬 idle 노드)가 생긴다.
  • 현행 자가청소(slot_service 시작 시 죽은 잡 잔재 제거)는 그 노드에 다음 잡이 떠야 돈다 → 재사용 안 되는 노드 잔재는 방치.
  • SIGKILL(trap 못 탐)·노드 크래시로 잔재가 생기는데 중앙 가시성 0 → "어디 몇 GB 새고 있나"를 모름.

2. 아이디어 — 생성/삭제 이벤트를 DB에

slot_service.sh가 /enroot dir/컨테이너를 만들/지울 때마다 작은 이벤트를 컨트롤플레인으로 push → 단일 DB에 기록. 생성됐는데 삭제 이벤트가 없는 것 = 누설로 바로 잡힌다.

2.1 이벤트 발생 지점 (slot_service.sh)

시점action대상
mkdir -p $OUT / enroot create 직후create/enroot/{USER}_{JOB}, edt-job-{JOB}, node
trap cleanup(enroot remove + rm -rf $JOBDIR) 시delete동일
시작 시 stale 청소(다음 잡이 죽은 잡 잔재 제거) 시delete(reclaimed)청소한 dir/컨테이너

2.2 전송 경로 (기존 백채널 재사용)

  • 결과 ingest(:7876)와 동일 토폴로지(gate 정터널 + 역터널). 새 엔드포인트 또는 ingest에 event 타입 추가: 
    POST :7878 또는 신규 :788x  /enroot_event
  { node, job_id, scratch_dir, container, action, ts, bytes? }
  • best-effort(실패해도 솔브 무방). delete 이벤트가 안 와도 그게 곧 "누설 신호"라 손해 없음.

2.3 DB 스키마(안)

CREATE TABLE enroot_events (
    ts DOUBLE, node VARCHAR, job_id VARCHAR,
    scratch_dir VARCHAR, container VARCHAR,
    action VARCHAR,        -- create | delete | reclaimed
    bytes BIGINT           -- 선택(스크래치 크기)
);
-- 또는 현재상태 뷰: 같은 (node,job_id) 최신 action이 create면 살아있음(=잔재 후보).
  • 누설 질의: create는 있는데 매칭 delete가 없고 + 그 job_id가 squeue에 없는 것 = 고아 잔재. 노드별 집계 → "n043에 3개 2.7GB×3 떠 있음".
  • DuckDB 단일 DB에 같이(이미 동시성 lock 있음). 7일 prune 같이 적용.

3. 대시보드(안)

  • 새 카드/탭: 노드별 /enroot 잔재(고아 create 수·추정 용량·최고령). srun 없이 한눈에.
  • 추세: 시간별 미회수 잔재 수 → 누설 추세 감시.

4. 고려사항 / 리스크

  • delete 누락 = 정상 신호: SIGKILL로 trap 못 타면 delete 이벤트가 없음 → DB가 "살아있음"으로 표시 = 정확히 누설 탐지. (단 실제로는 다음 잡이 reclaim하면 reclaimed 이벤트로 닫힘.)
  • 이중 계정: 같은 (node,job) create가 두 번 오면 멱등 처리. job_id가 키라 자연 멱등.
  • 오버헤드: 잡당 create/delete 2건 + reclaim뿐이라 미미.
  • 대안(가벼움): DB까지 안 가고, slot_service 청소 로그(cleaning stale)를 주기 집계만 해도 추이는 봄. 단 idle 노드 사각지대는 못 메움 → 이벤트 방식이 우월.

5. 범위

  • 지금은 구현 안 함. dev 브랜치에 이 문서로만 보관. 우선순위·여유 생기면 착수.
  • 착수 시: slot_service 훅(create/delete POST) + 신규 백채널/엔드포인트 + enroot_events 테이블 + 대시보드 잔재 카드 + 테스트 + 배포(컨테이너 사이클).
