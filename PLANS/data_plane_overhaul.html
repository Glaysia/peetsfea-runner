없앤다 /results.parquet 전체 DB 덤프 + :7877 bulk 압축파일 sink
새로 단일 증분 커서 스트림 API — 학습 주체는 마지막 커서 이후 변경분만 받아오고, since=0이면 전체를 컬럼형 스트리밍으로 빠르게 받는다
바꾼다 토이 http.server → 실 ASGI(백프레셔·연결관리)로 FD死 부류 제거

1. 왜 — 현재 구조의 근본 결함

현재 경로문제
GET /results.parquet (전체 DB 덤프)학습쪽이 매 라운드 전체를 다시 받아 재학습. 토이 서버에서 temp parquet 생성 + 동기 export → 부하·지연. FD 고갈 시 500 → 학습쪽 캐시 폴백 → R² 가짜 정체.
POST /bulk/<rid> (:7877 압축 산출물 sink)성공마다 AEDT tar.gz push → 단일 락 안에서 동기 압축 → 핸들러 스레드·CLOSE_WAIT 소켓 무한 누적 → FD死(1023/1024). incoming staging 428GB·15601개 10시간째 누수.
stdlib http.server 5개 한 프로세스연결수명/백프레셔/타임아웃 없음 → 누수가 구조적. 무거운 bulk가 가벼운 대시보드(학습 생명줄)를 같이 죽임.

→ 점-수정 불가. "전체를 통째로 옮기는" 두 경로 자체를 없애고, 변경분만 흐르는 증분 모델로 갈아엎는다.

2. 핵심 아이디어 — 단조 커서(write-version) 기반 증분

모든 결과 행에 단조 증가 seq(write-version)를 둔다. insert뿐 아니라 update(keep-best 교체)에도 bump. 학습 주체는 last_seq만 기억하고 seq > last_seq인 행만 받는다 → 진짜 "차이점"(신규 + 갱신된 베스트)만 O(변경분). 
-- 스키마(마이그레이션): 쓰기마다 증가하는 버전 컬럼 + 인덱스
ALTER TABLE single_simulation_results ADD COLUMN seq BIGINT;
CREATE SEQUENCE results_seq;
-- insert/upsert 시: seq = nextval('results_seq')  (update에도 재발급 = 변경 감지)
CREATE INDEX idx_results_seq ON single_simulation_results (seq);
  • 왜 finished_at 아니라 seq? 시계 역전·동시성 타이가 없고, keep-best update도 새 seq로 잡혀 학습쪽이 갱신된 베스트를 놓치지 않는다.
  • 재개 가능·멱등: 커서는 클라이언트가 보관 → 서버는 무상태. 재시도/크래시 후 last_seq부터 다시 받으면 끝.

3. 새 API — 증분과 full-sync를 한 엔드포인트로

학습쪽: last_seq 보관→ GET /api/results?since=last_seq→ seq>since 행을 seq순 스트리밍→ 응답 끝에 new max_seq↻ last_seq ← max_seq 
GET /api/results?since=<seq>&limit=<N>&format=arrow
  since=0           → 전체 (cold start / full-sync)
  since=last_seq    → 변경분만 (매 라운드)

응답: Arrow IPC 스트림 (컬럼형 바이너리). 헤더 X-Max-Seq = 이번 배치 최대 seq.
      행이 limit과 같으면 더 있음 → since=X-Max-Seq로 다음 페이지(루프).
요청의미학습쪽 동작
since=0전체 동기seq 0부터 페이지 루프 → 전체 적재(빠름, §4)
since=last_seq증분변경분만 받아 누적 학습 → R² 즉시 갱신

4. "전체를 다 받을 때도 빠르게" — 컬럼형 스트리밍

full-sync도 같은 엔드포인트(since=0)지만 느리면 안 됨. 토이 parquet-export(temp파일+동기)와 정반대로:

  • Postgres 서버사이드 커서(cursor(name=...))로 배치 fetch → 상수 메모리(전 행 적재 X).
  • 각 배치를 Apache Arrow RecordBatch로 변환해 IPC 스트림으로 write → 학습쪽 polars/pandas가 제로카피급으로 읽음(행별 JSON 대비 수~수십배).
  • 임시파일 0, 압축 sink 0, 락 0 → FD 누수 부류 자체가 없음.
  • 수만 행도 DB 스캔 속도로 흐른다. parquet가 꼭 필요하면 클라이언트가 Arrow→parquet 저장(서버는 스트림만).
async def stream_results(since, limit):
    async with db.server_side_cursor("SELECT ... WHERE seq>%s ORDER BY seq", since) as cur:
        async for batch in cur.fetch_arrow_batches(size=10_000):   # 상수 메모리
            yield arrow_ipc(batch)                                  # chunked 스트리밍
    # 헤더/트레일러로 max_seq 전달

6. 제거 대상 (명시)

완전 삭제:
• GET /results.parquet — 전체 DB 덤프 (→ /api/results?since=로 대체)
• :7877 bulk 압축 산출물 sink + edt_bulk_transfer.py + ArchiveStore 압축경로 + incoming staging (428GB 정리)
• 컨테이너 entrypoint의 bulk-push (성공 시 tar.gz 업로드) 호출
→ 학습은 raw AEDT 산출물이 아니라 DB의 결과 행(설계 파라미터·S-param·지표)만 쓴다. raw 아카이브가 정말 필요하면 web 경유가 아니라 오브젝트스토리지/노드 보관 + 참조로 out-of-band.

7. 마이그레이션 (dev 브랜치)

  1. 스키마: seq 컬럼 + 시퀀스 + 인덱스. 기존 행 backfill(현재 finished_at 순으로 seq 채움).
  2. 쓰기경로: insert/upsert(keep-best)에서 seq=nextval 부여(update에도).
  3. 읽기 API: FastAPI /api/results(Arrow 스트림, 서버사이드 커서). 대시보드 read API도 같이 이전.
  4. 제거: /results.parquet · :7877 bulk · entrypoint bulk-push · 압축 ArchiveStore.
  5. 학습쪽 계약: last_seq 보관 + since=last_seq 폴링(전체는 since=0 1회). RemoteDisconnected 시 같은 커서 재시도(멱등).
  6. 운영: uvicorn(워커 N) + LimitNOFILE systemd. ingest/lease/intake도 같은 ASGI 앱 라우트로 통합 or 분리.

-- seq 트리거
CREATE FUNCTION set_results_seq() RETURNS trigger AS $$
BEGIN NEW.seq := nextval('results_seq'); RETURN NEW; END $$ LANGUAGE plpgsql;
CREATE TRIGGER bump_seq BEFORE INSERT OR UPDATE ON single_simulation_results
  FOR EACH ROW EXECUTE FUNCTION set_results_seq();

-- keep-best upsert: 실제 개선일 때만 UPDATE(= seq bump) → 안 바뀐 행 재페치 0
INSERT INTO single_simulation_results (...) VALUES (...)
ON CONFLICT (request_id) DO UPDATE SET ...
  WHERE excluded.metric > single_simulation_results.metric;
