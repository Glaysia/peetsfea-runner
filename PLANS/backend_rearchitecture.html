재설계 — web 모놀리스 → 백엔드 분리 미구현 · dev · 19:00 착수

작성 2026-06-18 · 계기: 대시보드 텔레메트리 결측(차트 빈 구간) 근본진단 → 단일 web 프로세스 자원 고갈 · 구현·배포 안 함
한 줄. 지금은 web 프로세스 하나가 대시보드·ingest·벌크·intake·lease·라이선스·자원폴러·DuckDB를 전부 겸해 같은 2.7GB 메모리·1024 fd를 공유한다. 이걸 관심사별 프로세스로 분리하고 OLTP는 Postgres 백엔드, OLAP/export는 DuckDB(콜드), 대용량 산출물은 파일시스템으로 三분한다. 핵심 원칙: 감시(텔레메트리)·제어를 무거운 데이터플레인과 다른 fault domain에 둔다.

1. 현 구조의 문제 (진단 결과)

  • 단일 web 프로세스(edt_control_plane, EDT_ROLE=web)가 전부: 대시보드:8080 · intake:7875 · ingest:7876 · 벌크/아카이브추출:7877 · lease:7878 · 라이선스:7879 · 자원폴러(20s ssh) · 역터널 · DuckDB 호스팅(단일 writer 락).
  • DuckDB 오용: 임베디드 분석 DB(단일프로세스·단일writer)를 11GB 규모의 동시 운영 store로 사용 → 무거운 분석쿼리에서 OutOfMemoryException(2.7GB 한도).
  • 벌크 추출이 fd 다발 오픈 → 순간 Too many open files(1024).
  • 치명적 결합: 자원폴러(감시)가 같은 프로세스라, DB/HTTP/벌크 부하에 질식 → 폴러의 subprocess.run(ssh) 실패 → 빈 스냅샷 → 대시보드 전 지표 0-dip(실제 잡은 정상인데 측정만 실패). "감시 도구가 감시 대상과 운명을 공유"하는 구조 결함.

즉 DuckDB 결함이 아니라 임베디드 DB를 동시 운영 백엔드로 쓴 미스매치 + 모놀리스 결합. 초기 규모엔 맞았으나 11GB·300/h·동시 ingest+대시보드+벌크로 추월당함.

2. 설계 원칙

  • Fault domain 분리: 컨트롤·텔레메트리(저지연·경량)를 데이터플레인(무거운 I/O)과 다른 프로세스로. 감시는 절대 감시 대상과 한 프로세스에 두지 않는다.
  • OLTP / OLAP 분리: 핫 운영데이터는 client-server DB(Postgres, MVCC) — 동시 read/write가 서로 안 막힘. 콜드 분석·parquet export는 DuckDB가 parquet/archive 위에서(라이브 store 아님).
  • 대용량은 DB 밖: aedtresults 산출물은 파일시스템 ArchiveStore, DB엔 참조만(현행 유지).
  • 프로세스별 자원 경계: 각 systemd 유닛에 LimitNOFILE·MemoryMax 지정 → 한 서비스가 호스트를 못 말아먹음.
  • 쓰기 단일화·백프레셔: ingest writer를 분리하되 Postgres 풀로 동시성 확보. 대시보드는 read 전용 연결.
  • 현행 토폴로지 보존: 슈퍼컴 워커의 역터널 push(:7876/:7877), keeper의 sbatch 오케스트레이션은 그대로 — 수신측만 Postgres로.

4. 데이터 배치 (三분)

  • Postgres(핫·OLTP): sim_results(메타+telemetry, 대용량 json은 참조), resource_snapshots(시계열), priority_queue/sweeps. MVCC라 ingest 쓰기와 대시보드 읽기가 서로 차단 안 함 → DuckDB 단일락·OOM 문제 소멸.
  • 파일시스템 ArchiveStore(대용량): aedtresults 산출물 — 현행 그대로, DB엔 경로 참조만.
  • DuckDB/parquet(콜드·OLAP): 다운로드/대규모 분석은 Postgres에서 parquet로 export하거나, archive parquet 위에서 DuckDB로. 라이브 운영 store 역할에서 은퇴.

5. 마이그레이션 단계 (19:00 착수 순서)

  1. Postgres 기동: 로컬 systemd(또는 컨테이너), peetsfea DB·롤·연결풀. 자원경계 설정.
  2. 스키마 이식: DuckDB 테이블 → Postgres DDL(타입 매핑, 인덱스: ts·terminal_state·version). single_simulation_store를 Postgres 백엔드로 추상화(드라이버 교체 가능하게).
  3. 데이터 이관: 기존 11GB DuckDB → Postgres(핫 구간만; 콜드는 parquet 아카이브로). COPY/배치.
  4. 서비스 분리: edt_control_plane의 web 역할을 3개 유닛(control/ingest/dashboard)으로 split. 각 systemd 유닛 + LimitNOFILE/MemoryMax.
  5. 폴러 이전: 자원폴러를 control 프로세스로(데이터플레인과 격리). 스냅샷은 Postgres에 write.
  6. 컷오버: 워커 역터널 수신을 ingest 유닛으로, 대시보드를 read-only 연결로. 검증 후 DuckDB-store 폐기(export 전용만 잔존).
  7. fd/메모리 회귀검증: 부하 중 텔레메트리 결측 0 확인.

6. 경량 대안 (운영부담 줄이려면)

  • SQLite(WAL): client-server는 아니나 WAL 모드로 동시 reader + 단일 writer 가능 → DuckDB보다 OLTP 적합. 다만 분석쿼리·확장성은 Postgres만 못함.
  • DuckDB-owner 단일 프로세스: DuckDB를 유지하되 DB 전용 프로세스 뒤에 두고 모두 IPC/HTTP로 질의 → 메모리·fd가 한 곳에 갇힘. 프로세스 분리만으로 결합 문제 일부 완화(중간 단계).
  • → 권장: 프로세스 분리는 필수(원칙 2). store는 Postgres가 정석이나, 1차로 "프로세스 분리 + DuckDB-owner"만 해도 텔레메트리 결측은 사라짐. 시간/부담 보고 단계 선택.

7. 리스크 / 고려사항

  • 단일 노드(5950x): Postgres 동거 OK, 자체 자원관리가 오히려 격리에 유리.
  • +1 서비스(Postgres) 운영부담 ↔ 안정성 이득. 백업/마이그레이션 절차 필요.
  • 이관 중 무중단: dual-write 또는 짧은 점검창. 진행 중 결과 유실 방지(역터널 버퍼).
  • 스키마 호환: single_simulation_store API를 백엔드 추상화로 감싸 드라이버 교체 — 호출부(대시보드/ingest) 변경 최소화.
  • 현행 보존: keeper·slot_service·역터널·ArchiveStore·라이선스 제어 로직은 그대로(수신측 store만 교체).
