현재 운영 핵심 (2026-06-19)

  • 한 번 돌고 완전히 꺼진다: 단일 컨테이너는 EDT_SLOT_COUNT=1, EDT_MAX_SIMS=1로 1건만 처리하고 종료한다. 프로세스, pyaedt 세션, 임시 디렉터리, 마운트 상태를 다음 솔브로 가져가지 않는다.
  • 상시 예열 풀은 현행에서 쓰지 않는다: edtmgr로 AEDT를 계속 붙잡아 두는 방식보다, 매 솔브마다 프로세스와 컨테이너를 닫아 누수와 세션 오염을 끊는 것을 우선한다.
  • 잡 출생 제어: 잡 수 구간을 나누지 않고 2분마다 홀짝 tick을 실행한다. 홀수 tick은 새 잡 4개 제출만, 짝수 tick은 가장 늙은 RUNNING 잡 1개 종료만 수행한다. squeue는 최대 15개, 정상 목표는 RUNNING 10 + PENDING 5다.
  • PENDING 정리: PENDING reason이 빈값/None/null/(null)/pending이 아니면 정상 대기열로 보지 않는다. Priority/Resources/ReqNodeNotAvail 등은 cap과 무관하게 즉시 취소한다.
  • N 결정: 새 잡은 현재 elec_solve_hfss 실측을 보고 계단형 LUT로 컨테이너 수를 정한다. 0~90은 20, 100은 15, 이후 10 solve마다 1씩 낮춰 150 이상은 10으로 둔다.
  • 포화 감압: 2분 루프 여섯 번마다 라이선스 사용량을 확인하고, solve가 150을 넘으면 가장 늙은 RUNNING 잡 1개를 추가로 내린다.
  • 데이터 플레인: 슈퍼컴엔 DB 없음. 컨테이너가 결과를 gate 경유 역터널(:7876 JSON, :7877 대용량)로 로컬 데몬에 push한다.
  • 운영 파티션: 제출 런처는 cpu2/gpu1을 우선 사용하고, gpu* 잡은 --gres=gpu:2와 CUDA_VISIBLE_DEVICES 핀닝으로 GPU를 분산한다.

1. 전체 데이터 흐름

제어 큐/잡 단명 컨테이너 저장/관측

핵심은 장수 AEDT 세션이 아니라 완전한 소멸이다. 컨테이너는 한 번만 풀고 결과를 보낸 뒤 종료하며, keeper가 잡 출생률과 squeue 완충량으로 전체 처리량을 맞춘다.

2. 목표 토폴로지

단위현행 값비고
계정(account)1개단일 계정 기준. 다계정 확장은 현재 범위 밖.
잡(SLURM sbatch)squeue 최대 15개정상 목표는 RUNNING 10개 + PENDING 5개. PENDING은 reason None 계열만 인정하며, Priority/Resources 등은 즉시 취소. 제출은 노드별 균등 분산.
잡 수명최대 20분2분 홀짝 루프에서 더 일찍 내려갈 수 있다. 종료 시 진행 중 컨테이너와 AEDT도 같이 정리된다.
컨테이너 수 N잡 출생 시 10~20개현재 solve 실측을 LUT로 읽어 결정. 컨테이너 출생은 stagger로 분산.
AEDT 실행 단위컨테이너당 1회EDT_SLOT_COUNT=1, EDT_MAX_SIMS=1. 완료 후 재사용 없이 종료.
동시 실행 목표solve 100 근처과포화는 LUT와 12분 감압으로 낮춘다. solve >150이면 가장 늙은 잡을 추가 종료.
워커 GPUgpu1: 2 (gres)워커별 CUDA_VISIBLE_DEVICES=idx%2 핀닝 · cpu2는 CPU only.

3. 왜 완전 종료인가

폐기한 방식

AEDT를 오래 붙잡아 두는 예열 슬롯 풀은 기동 비용을 줄일 수 있지만, 실가동에서는 세션 상태, pyaedt 연결, 임시 파일, 메모리 사용량이 다음 솔브로 넘어가는 위험이 더 컸다.

  • 오래 산 프로세스가 상태를 들고 있어 실패 원인 분리가 어려움.
  • 라이선스와 gRPC 연결을 계속 물고 있어 회복 동작이 불명확함.
  • 잡을 내렸을 때 OS가 한 번에 회수하는 경계가 흐려짐.

현행 원칙

콜드스타트 비용은 받아들이고, 대신 컨테이너 경계를 강하게 만든다. 한 컨테이너는 한 solve만 수행하고 결과 push 후 종료한다. enroot 제거까지 끝나야 해당 solve의 런타임 상태가 닫힌 것으로 본다.

  • 실패와 누수를 컨테이너 하나의 생애 안에 가둔다.
  • 잡 교체와 squeue PENDING 버퍼로 콜드스타트 공백을 흡수한다.
  • 정리 기준이 명확하다: AEDT 종료, pyaedt 종료, enroot 제거.

4. 잡 출생 제어

every poll:
    cancel_pending_jobs_unless_reason_is_none_like()

every 2 minutes:
    if squeue_count >= 15 and queue_is_stuck:
        stop_oldest_running_job()
        submit_jobs(1, spread="node-even")
        return

    if tick_number is odd:
        submit_jobs(4, spread="node-even", squeue_cap=15)
    else:
        stop_oldest_running_job()

every sixth tick:
    if license_solve_in_use > 150:
        stop_oldest_running_job()

세부 정책과 LUT 표는 PLANS/job_birth_controller.html을 기준으로 한다.

5. 자원 / 파일시스템 / 라이선스

  • /dev/shm, /tmp 직접 사용 금지 → 잡 전용 job_tmpfs / job_disk 사용.
  • 잡 시작 시 /enroot/{USERNAME}_{SLURM_JOB_ID} 계열 작업 공간을 만들고, 잡 종료 trap에서 삭제.
  • 라이선스는 상시 점유 세션이 아니라 elec_solve_hfss 실측 기반 LUT와 12분 포화 감압으로 제어.
  • 슈퍼컴 쪽에는 결과 DB를 두지 않는다. 결과와 대용량 산출물은 로컬 수신 데몬으로 push한다.

6. 부가 서비스

Intake :7875 신규

peetsfea sweep toml + 개수 N 수신 → 랜덤 샘플 fixed toml × N → 대기 큐 적재 → 컨테이너가 하나씩 소비.

대시보드 :8080 가동

결과 DB + 실시간 부하(ResourcePoller: scontrol·lmstat 폴링)를 읽기 전용으로 시각화한다. 개요, 컨테이너 부하, 실패, 자원 시계열을 한 화면에서 본다.

아카이브 신규

project_directory를 누적해 20GB 단위 묶음(solid) 압축. 2TB 초과 시 가장 오래된 묶음파일 1개 삭제. 복원이 느려도 무방.

7. 현재 구현 기준

1

컨테이너 생애 핵심

잡 내부 서브 오케스트레이터가 N개 컨테이너를 stagger로 띄운다. 각 컨테이너는 fixed toml 1개를 처리하고 결과 push 후 종료한다.

2

잡 생애 핵심

keeper가 2분마다 홀짝 tick을 실행한다. 홀수 tick은 새 잡 4개를 요청하고, 짝수 tick은 가장 늙은 RUNNING 잡을 내린다. squeue 15를 넘기지 않고 PENDING 5개를 완충으로 둔다.

3

관측과 저장

결과는 로컬 DuckDB와 아카이브로 들어가며, 대시보드는 read-only 관측면으로 유지한다.
